# research-sim

The downstream simulator of the UnFrack.It UTxO-management research. This folder holds three parts of it: the history reader, the simulator core and the baselines.

The history reader turns a cardano-db-sync database into the simulator's inputs, for given wallets and windows. For each wallet (a stake credential) and window it writes one history file. The file holds the wallet's UTxO set at the window's start, then every event of the window in chain order: deposits, held UTxOs consumed, spends with their intents, self-reorganizations, and 30-day marks. The reader also writes a wallet's state at the snapshot block, and computes the census, near-cap and collateral quantities as separate commands.

The simulator core replays those histories offline: a ledger kit that assembles and checks transactions exactly, wallet states, a bridge to the treatment, the method contract every selector implements, the arms and their run plans, the replay engine, and the synthetic shapes with their intent streams. It reads no database and no chain.

The baselines are the external selectors the treatment is compared with: `csl-lf`, `csl-ri`, `cjs-rrri`, `evo-lf`, `blaze-wd`, `lucid-lf`, `mesh-rrri`, `typhon-lp`, `helios-sf`, `cml-lf`, `cml-ri`, `cometa-lf`, `lace-rrri`, `adalite-lp`, `yoroi-lf` and `apollo-macs`. Each runs at its library's defaults through an adapter that implements the method contract. `lace-rrri` runs the Lace wallet's transaction builder, which no package publishes, from a local build of the wallet's source ("Building Lace's source" below). `adalite-lp` runs the AdaLite wallet's planner, which no package publishes either, from a local build of its source (the `adalite-lp` paragraph under "Replay path" below). `yoroi-lf` runs the Yoroi wallet's send flow, also from a local build of the wallet's source ("Building Yoroi's source" below). `apollo-macs` runs Apollo's transaction builder, a Go library, in a helper process through the bridge (`src/methods/helper.mjs`, "Building the helpers" below). A builder survey also runs Mesh's selectors with Mesh's own constraint callbacks, the Evolution SDK's `unfrack` option and CSL with `prefer_pure_change` set.

A few terms recur below. The extraction is the study's sampling tool in this repository, `tools/research-corpus`; it builds its tables in a database schema named `study`. A frame is the window a wallet was sampled for: `recent` (the 365 days ending at the snapshot block) or `peak` (the busiest 73 epochs since the Mary hard fork). Every sampled wallet is in one split: exploration, which may be read at any time, or confirmation, which is read only after the study's analysis scripts are frozen on chain. The treatment is the code under test, UnFrack.It's planner and selection rule; its files are published with the study's archive, not in this repository.

The study's hypotheses are numbered H-1 to H-12. This README refers to two of them, by these labels:

- H-7 (descriptive): the Largest-First and Random-Improve selections, as libraries extend them to multi-asset values, drag unrelated tokens, grow change outputs toward the value cap, fail to build, and pay more than necessary.
- H-12: UnFrack.It's own input selection completes more of the spends a wallet's balance allows than the library selectors do, at no greater cost for the spend and the tidying that follows it.

The study's run replays each wallet's observed state for two questions, labeled Q1 and Q2 on the plan's entries and in the records' `hypotheses`: Q1, whether UnFrack.It's change output strategy fails less and costs less over time than the change each library builds (each library's own change against UnFrack.It's change, on the library's inputs); Q2, whether UnFrack.It's H-12 input rule does the same against each library's inputs, both under UnFrack.It's change. "Arms and run plans" below lists the jobs.

## Where it may run

- **Preprod**: anything, at any time, through a read-only role. All development and every test of the reader runs there.
- **Mainnet, before the final freeze**: only the `live-fire` command, after the hypotheses record is on chain, and only on the wallets an extraction live-fire run picked ("Live-fire checks" below). Every other command is refused.
- **Mainnet, after the final freeze**: only the study's own run, and only once the extraction tool's study run for the final freeze has finished. Every wallet a command reads must be in that run's sample (`study.sample`), and a confirmation-split wallet still needs `--analysis-freeze-tx`. The census is the one exception: it reads every eligible wallet of the recent frame, as the study's census of the snapshot does. Debugging after the final freeze uses the exploration split, the synthetic shapes and preprod only; before it, the live-fire checks are the only runs on mainnet wallets, and once a study run of the final freeze is recorded, the live-fire command is refused.

Every command that connects reads db-sync's `meta` table first, and on mainnet it passes the gate below before it reads any wallet. The run the gate reads fixes the snapshot and the windows. The mainnet code paths, such as the ImmutableDB byte source, are tested against preprod's own node.

`EXPLAIN ANALYZE` executes its query, so the code refuses it on mainnet in every case; plain `EXPLAIN` is allowed everywhere.

### The mainnet gate

The gate is one check in the connection (`src/history/db.mjs`, queries in `sql/gate.sql`), made after the network is read and before the connection reaches any command. A mainnet connection names its path, which the code that opens the connection sets; no command-line option can set it. There are two paths, `final-freeze` and `live-fire`, and any other mainnet connection is refused, with the reason.

**The final-freeze path.** The extraction tool's driver checks the final freeze record, the code manifest and the check log before its study run reads a wallet, and records that run in its `study` schema. The gate reads that record and does not verify the freeze again. It passes when:

- the role can read `study.run` and `study.param`;
- exactly one run's `freeze` row has the role `final-freeze`, and that run is recorded for mainnet;
- that run's `mode` row is `study`, and it has a `finished` row, which the driver deletes whenever the run starts or resumes and writes as its last step;
- its `snapshot` row is a block fixed by rule, with its id, hash and last transaction id, and its `windows` row gives both windows' blocks and transaction-id bounds;
- each `study` table this code reads (`frame`, `sample`, `draw_group`, `draw_summary`, `franken`, `txo`, `txo_asset` and `asset`) carries that run's mark, the comment `research-corpus run <id>` that the extraction's runner writes on every table a step builds, so the samples and flags read are that run's.

Every command on the connection then uses that run's snapshot block and windows, as `--extraction-run` would give them, and checks them against the database. A `--snapshot` naming any other block is refused, and so is an `--extraction-run` naming another run.

The commands on the connection then read only wallets of that run's sample. `history` refuses a wallet named by `--wallet` or `--wallets` that is not in `study.sample`; a stake address is looked up to learn its stake-credential id, and nothing else of the wallet is read before the refusal. `--from-study` reads the sample itself. `census` and `near-cap` refuse `--all-wallets` and any wallet named outside the sample; with `--from-study`, near-cap reads the union of the random samples, and the census reads the recent frame's eligible wallets, which is its population. A role that cannot read `study.sample` reads no wallet on mainnet. A refusal names no wallet. The extraction's own refusals follow: a wallet its reconstruction check excluded, and a confirmation-split wallet without `--analysis-freeze-tx`.

**The live-fire path.** Only the `live-fire` command opens it, before the final freeze. Before its first query, the command reads the extraction run's pick of the simulator's live-fire wallets and checks it (`src/study/checklog.mjs`); the gate then reads the pick again and passes when:

- the mainnet check log's sequence and digest chain hold;
- the log has the extraction run's `live-fire-start` entry, which that tool writes only after its gate has found the hypotheses record on chain, so the hypotheses freeze is on chain;
- the run's `live-fire` end entry kept the pick (`sim_wallets: kept for the simulator checks`), and no successful `cleanup` of the run follows it;
- `sim/wallets.json` is in the run's directory and names that run, mainnet, the test value of h that the run's entries record, the snapshot block, and one to ten stake addresses;
- the pick is the one the command read;
- the role can read `study.run` and `study.param`, and no run of the final freeze is recorded there.

The grant is the pick. Every command on the connection reads the pick's snapshot block, given by hash, and no other, and takes no `--extraction-run`. It reads only the pick's wallets and no `study` table, and refuses `--from-study` and `--all-wallets`. On a test network the command applies the same restriction to its stages without the gate.

## Install

Node 24 is required (`engines` in `package.json`). From this folder:

```
npm ci
npm test
node src/cli.mjs help
```

`npm test` needs no treatment and skips the unit tests that do. It also skips the tests that run `lace-rrri` or `yoroi-lf` when that wallet's source has not been built, and those that run `apollo-macs` when its helper has not been built. The bridge's test compares a bridged `csl-lf` with `csl-lf` on the MI-3 shapes, and on a preprod history file when `RESEARCH_SIM_BRIDGE_HISTORY` names one.

Building Lace's source. The Lace wallet's transaction builder is a private package of its repository, `@lace-contract/cardano-context` in `input-output-hk/lace` at commit `4d553bd696903c7a78652ab61da5237165008195` (the lace-extension 2.5.1 release), so `lace-rrri` runs it from a local build that no file in this repository holds:

```
node scripts/build-lace.mjs --clone <a clone that holds the commit>
node scripts/build-lace.mjs --fetch <a new directory>
```

The script checks the git object hash of each path it uses at that commit against the pins in `src/methods/lace-source.mjs`: the `tx-builder` and `input-selection` directories of `packages/contract/cardano-context/src/` and the three modules they import (`signing/getUniqueSigners.ts`, `estimate-signed-tx-size.ts`, `common/time.ts`). It extracts them with `git archive`, never from a working tree, and bundles them with the tool's pinned esbuild 0.28.1 into `build/wallets/lace/` (gitignored). The `@cardano-sdk` packages stay external, so the tool's installed `core` 0.47.1, `crypto` 0.4.7 and `tx-construction` 0.29.1 load, the versions the package's own manifest pins. Beside the bundle it writes the repository's license and `source.json`, which records the commit, each path's hash, the esbuild version and the bundle's SHA-256. `--fetch` makes a shallow, blobless clone of that one commit. `lace-rrri` refuses to load when the build is missing or its record differs from the pins, and its message names the script.

Building Yoroi's source. The Yoroi wallet's send flow is a set of modules inside its mobile app, `mobile/packages/` in `Emurgo/yoroi` at commit `d8e3d3f93fb772f0b6bd2296e45bfac7da4fb9d6` (the v7.0.5 release), so `yoroi-lf` also runs from a local build:

```
node scripts/build-yoroi.mjs --clone <a clone that holds the commit>
node scripts/build-yoroi.mjs --fetch <a new directory>
```

The script checks the git object hash of each path it uses against the pins in `src/methods/yoroi-source.mjs`. Those paths are seven directories of `mobile/packages/`: `cardano-wallet` and `tx`, and the Yoroi packages they import on the send path (`api`, `common`, `logger`, `portfolio`, `types`). It also checks the repository's license and the app's lockfile, `mobile/package-lock.json`. It extracts them with `git archive` and bundles the send flow with the same esbuild into `build/wallets/yoroi/`. Yoroi's modules are marked free of side effects, so a module the send flow does not use is left out. A build whose kept code would load any package other than Node's `buffer` and CSL fails. The app reaches CSL through `@emurgo/cross-csl-mobile`, a bridge to a native build. The bundle uses `@emurgo/cross-csl-nodejs` over the Node.js build of CSL instead, as Yoroi's own test setup does (`mobile/jest.setup.js:41`). The two bridge packages and immer are fetched with `npm pack` and bundled in. Each tarball's SHA-512 must equal the integrity Yoroi's lockfile records. CSL 14.1.2, the version that lockfile records, is not bundled. It is installed here under the npm alias `cardano-serialization-lib-nodejs-14.1.2`, at the same integrity, and the bundle loads it at run time. Beside the bundle the script writes Yoroi's license (Apache-2.0) and `source.json`. That file records the commit, each path's hash, the npm packages, the CSL pin, the esbuild version, the modules bundled and the bundle's SHA-256. `yoroi-lf` refuses to load when the build is missing or its record differs from the pins, and its message names the script. Lace's, AdaLite's and Yoroi's build scripts share their clone, check and extraction code (`scripts/wallet-source.mjs`).

Building the helpers. A library in another language runs in a helper process, one per method in each process that builds, which the bridge (`src/methods/helper.mjs`) speaks to in JSON lines over its standard input and output; the module's header comment defines the schema. Each helper's source and lockfile are under `helpers/<name>/`, and one command builds one into `build/helpers/<name>/` (gitignored):

```
node scripts/build-helpers.mjs apollo
```

`apollo` is Go: Apollo v2.2.1 (`github.com/Salvionied/apollo/v2`, the release tag's commit `12d4a1c77cc1f991231d6ffca306ceef61dbabd0`), which needs Go 1.26.10 or later. Go must be on the `PATH` as `go` (`RESEARCH_SIM_GO` may name the go command instead); without it the script stops and says so. The script downloads the modules into Go's module cache, checks them against `go.sum` (`go mod verify`) and the release's commit against the module's recorded origin, and builds without cgo, with `-mod=readonly`, `-trimpath` and `-buildvcs=false`, so the executable depends on the helper's source and the toolchain, not on the repository's commit. Beside the executable it writes `build.json`: the SHA-256 of each source file and of the whole source, the toolchain, the module's version, sums and commit, and the executable's SHA-256. A helper method refuses to load when the record is missing or differs from the source in the tree or from the executable, and its message names the command. Its version names the executable's SHA-256, so a run's code manifest records which helper built it. A helper that exits or answers out of turn stops the job with its standard error's last lines; nothing of it is recorded as a spend's outcome. The pool's memory readings of a worker count its helper processes.

The tool has its own `package.json` and lockfile. Its runtime dependencies are `pg` (node-postgres) 8.23.0 and the three baseline libraries that come from npm (`@cardano-sdk/input-selection`, `@evolution-sdk/evolution` and `@meshsdk/transaction`), each pinned with its npm integrity. cardano-serialization-lib is not among them. `npm ci --ignore-scripts` installs the same tree without compiling `chacha-native`, an optional native dependency of `chacha` (which `@cardano-sdk/key-management` uses), and `chacha` then loads its JavaScript implementation; no adapter calls it.

cardano-serialization-lib (CSL) comes through the treatment's `cslkit.mjs`, so that the reader, the treatment and every adapter but `yoroi-lf` share one CSL instance. `yoroi-lf` runs on the CSL its wallet pins, 14.1.2. This folder's lockfile holds that build under the alias `cardano-serialization-lib-nodejs-14.1.2`, so that no code that loads CSL by its own name can reach it. The lockfile holds no other CSL build: the treatment directory carries its own `package.json` and lockfile, whose SHA-256 digests the pins list beside the treatment's source files, and the `csl-*` adapters refuse to run unless `cslkit.mjs` reports `CSL_VERSION` 17.0.0 (`src/methods/csl.mjs`). `--treatment <dir>` names the directory holding the treatment's files, and `--treatment-pins <file>` a list of their SHA-256 digests, one `<64 hex><two spaces><file name>` per line; `replay` and `fidelity` use `data/treatment-pins.txt` when `--treatment-pins` is absent. Before anything is imported, every listed file's digest is compared with the file in that directory, and any difference refuses the load, naming the file. The `history` and `census` commands need both options (they have no default list, and `--treatment` alone is refused); `replay` and `fidelity` need `--treatment`; `near-cap` and `collateral` need neither.

## The database

cardano-db-sync 13.7 with the core `tx_out` layout, `tx_out` values enabled, and multi-asset, metadata, Plutus and ledger data inserted; never `prune`, `bootstrap` or `only_utxo`. The queries read schema `public`, and the extraction's `study` tables when the role can read them (its samples with their split and reconstruction-check exclusion, its franken flags and its life table, plus, on mainnet, the run records the gate reads). Each filters on an indexed column, except the chain-wide collateral measurement and the epoch boundaries of the near-cap command, which read their tables in one pass each. Reads by transaction, reference or wallet go in batches (200 transactions, 1,000 or 2,000 output references, or 500 wallets per statement), so that no single statement runs long. Nothing is created anywhere.

Connection: `PGHOST`, `PGPORT`, `PGDATABASE`, `PGUSER`. The password comes from the file `PGPASSFILE` names (libpq's format, mode 0600). It is read when the connection opens and never printed or logged. Every session is read only.

## Transaction bytes

Every spend's intent is read from the transaction's own bytes:

- `tx_cbor` (the default on a test network): db-sync's `tx_cbor` table, kept when db-sync runs with its `tx_cbor` option on.
- `immutable` (the mainnet source): the node's ImmutableDB chunk files, read without modification, locally or over SSH with `cat`, `stat` and `dd` (`--bytes immutable --immutable-dir <dir> [--immutable-host <host>]`). Each block is found through its chunk's secondary index and checked against the index entry's CRC-32. Each transaction is reassembled from the block's body, witness-set, validity and auxiliary-data segments with their original bytes.

The on-disk format is read from `IntersectMBO/ouroboros-consensus` at commit a0e8f68afeac411fcc8262f9271438314a87ed02: `ImmutableDB/Impl/Util.hs`, `Impl/Index/Secondary.hs` and `Chunks/Internal.hs`, and the era envelope in `ouroboros-consensus-cardano`, `Cardano/Node.hs` (`encodeDiskHfcBlock`). Every ledger path below is in `IntersectMBO/cardano-ledger` at commit 391db20866113f08bc6317cb5c341304365986c6; the block layout is the Conway CDDL's (`eras/conway/impl/cddl/data/conway.cddl:8-14`).

Every transaction read from either source must hash to db-sync's transaction hash (BLAKE2b-256 of its body bytes) and have the size db-sync records, the ledger's size: the length of `[body, witnesses, auxiliary data or null]`, which leaves out the validity flag from Alonzo on (`eras/alonzo/impl/src/Cardano/Ledger/Alonzo/Tx.hs:377-385` and `:482-496`). A mismatch stops the read with the transaction named.

It also refuses an option given twice, flags included, except `--set`, `--wallet`, `--window` and `--history`, which repeat. Each command has its own options: `--from-study` takes a value (`random` or `all`) for `history` and `study`, and is a flag for `census` and `near-cap`; `--validity`, `--explain`, `--all-wallets`, `--keep-for-debug` and `--cleanup` are flags. The reader also checks the values a typo would change: `--from-study` (`random` or `all`), `--bytes` (`tx_cbor` or `immutable`), `--plan` (`recent` or `peak` for `replay` and `plan-shards`; `synthetic`, `preprod` or `corpus` for `study`) and `--window`, and requires a positive whole number for `--workers`, `--reps`, `--days` and `--batch`, a label of letters, digits, `-` and `_` for `--machine`, a positive number of GiB for `--memory-budget`, and `k/n` with 0 <= k < n for `--shard`. `--limit-ms` and `--answer-limit-ms`, which earlier versions took, are refused with their reasons. The options are listed once, in `src/options.mjs`, which `study` and `live-fire` read for theirs; their own checks of what a plan or a run uses stay.

Common options: the database options are `--expect-network <name>`, `--snapshot`, `--extraction-run`, `--bytes`, `--immutable-dir`, `--immutable-host`, `--set`, `--treatment` and `--treatment-pins`, and `history`, `census`, `near-cap` and `collateral` take all of them (`--treatment` and `--treatment-pins` are used by `history` and `census` only). `--expect-network <name>` refuses any other database; `--snapshot tip|<block hash>|<block id>` (default `tip`); `--extraction-run <params.json>` takes the snapshot and the windows from an extraction run of `tools/research-corpus` and checks them against the database (the `live-fire` command's `--extraction-run` names a run ID instead; on mainnet both come from the gate: `--snapshot` may name only the gate's block, and `--extraction-run` only the gate's run); `--bytes`, `--immutable-dir`, `--immutable-host`; `--treatment`, `--treatment-pins`; `--set <name>=<value>` changes one setting; `--explain`, for `census` and `collateral` only, keeps the plain `EXPLAIN` plan of their queries; `--analysis-freeze-tx <hash>`, the mainnet transaction whose signed record freezes the analysis scripts; without it a confirmation-split wallet is refused, and with it the run records the hash.

A wallet the extraction's reconstruction check excluded is refused. `--all-wallets` takes every key stake credential with an output, for a test network.

### Workers and watchdogs

No time limit decides a result, and no record depends on the machine or on how many workers run. Every replay and method answer runs to completion, and its time goes to `timings.jsonl` as timing context only.

CSL's calls are synchronous and cannot be interrupted from inside, so a watchdog far above any expected time guards against work that hangs: 24 hours per replay job (`REPLAY_WATCHDOG_MS` in `src/replay/pool.mjs`). When a watchdog falls, the worker is stopped and the work is set aside: nothing of it is recorded, and it runs again at once in a fresh worker with its watchdog doubled, as often as it takes to complete. A stopped replay runs again from its start and rewrites its job's spool. A replay wallet's segment is marked done only once each of its jobs has completed, so its records are byte for byte those of a run that no watchdog stopped.

An error the machine can cause is never recorded on its first appearance (`src/kit/machine.mjs`). These are a `RangeError` (a heap or buffer that cannot grow, or a call stack too deep), a WebAssembly `RuntimeError` (a library whose memory cannot grow aborts) and a worker that exits or errors during a job. A `RangeError` with an `ERR_` code is Node's check of an argument, such as a buffer read past its end, and is excepted. The job runs again once in a fresh worker. That worker records such an error as it records any other exception: as a method's failure of class `other` or a planner's refusal. Only what happens there stands. An error that is not the machine's stops the run. A replay worker that dies during a job (it exits, or a signal or the kernel's out-of-memory killer stops it) has the job run again in a fresh worker that records machine errors, with the job's memory estimate doubled. If that worker dies too, the job runs once more alone, with the whole memory budget. A third death at the same point of the job fails it, with a message naming the job, and stops the run.

A replay stage runs several wallets at once, so that one wallet's slowest job does not leave the other workers idle. It keeps one queue of the jobs not yet handed to the pool, in wallet order and in job order within a wallet, and hands the pool a job whenever fewer than twice the worker count of jobs are in the pool. So while one job waits in the pool for memory, the pool has later jobs it may start ("Worker memory" below). It opens the next wallet whenever fewer than twice the worker count of jobs are queued and fewer than twice the worker count of wallets are open. A wallet closes when its last job ends: its segment is compressed and its done file written while the other wallets' jobs run, one wallet at a time. Wallets close in any order, and the stage joins them in wallet order at its end, so the order changes no record. The log's `window` entry gives the worker count, the queue's target, the jobs the pool may hold and the cap on open wallets.

`--workers` takes any positive whole number; a count suited to the machine is at most its physical cores, fewer when memory is short. The study's log keeps the count, the memory budget and the machine apart from the options, as `machine`: `{ workers, memoryBudgetBytes, cpuModel, logicalCores, totalMemoryBytes, os, osRelease, platform, wsl, node, v8 }`. A replay stage keeps them in `machines/<label>.json` ("Outputs" below), never in its `run.json`. The printout and the log's end give the pool's counts beside the totals: `workers` (`started`; `recycled` after 40 jobs and `recycledBySize`; `watchdogStops`; `machineReruns`, and among them `outOfMemoryReruns`, those after a worker died; `admissionWaits`, `admissionPasses`, `aloneRuns` and `estimatesRaised`, "Worker memory" below). The log notes each watchdog stop and machine rerun with the job it stopped. None of these is in the totals or the records. Times are comparable only between runs on similar machines at similar worker counts.

### Worker memory

Each replay worker is a child process (`child_process.fork` with an IPC channel, `src/replay/pool.mjs`), so its memory can be measured and the kernel's out-of-memory killer stops one worker, not the run. With the treatment loaded, an idle worker holds about 204 MiB and starts in about 0.6 s. A worker exits when its parent's channel closes, so none outlives a killed run.

The budget. `--memory-budget <GiB>` (`replay` and `study`, which passes it to its replay stages) is the memory the workers may hold, by default 80% of `MemAvailable` in `/proc/meminfo` when the pool starts. It changes no record. It is not among the options that `run.json` and the study's header record, and it is recorded with the machine as `memoryBudgetBytes`: in the invocation's entry of a replay stage's `machines/<label>.json` (with the pool's counts as `pool`), and in the study log's machine record when it is given.

The estimate. Each job has an estimate of its worker's peak resident size: 600 MiB + 29 KiB × U + 36 KiB × E, where U is the wallet's UTxOs at the start plus the UTxOs its window's deposits add, and E its window's events (`MEMORY_ESTIMATE` and `jobEstimate` in `src/replay/pool.mjs`). The coefficients are the upper envelope with the least total excess over the heaviest job measured on five wallets, on CSL 17.0.0's WebAssembly build. M2 and H5E01 were measured one job per fresh worker at 4 workers; the other three are from the heavy probe ("The heavy probe" below), one process per job. A job stopped before its end gives a lower bound.

| Wallet | U | E | Heaviest job | Its peak |
|---|---|---|---|---|
| M2 | 3,010 | 18 | `evo-lf` | 596 MiB |
| H5E01 | 5,015 | 100 | `evo-lf`, stopped at 5 minutes | at least 736 MiB |
| H20E01 | 20,015 | 100 | `evo-lf`, stopped | at least 1,066 MiB |
| H20E05 | 20,079 | 500 | `cjs-rrri` (`evo-lf` not run) | 1,171 MiB |
| H3E6 | 3,962 | 6,000 | `evo-lf`, stopped | at least 910 MiB |

The estimate gives these wallets 686, 746, 1,170, 1,186 and 923 MiB, and a small shape such as S1 601 MiB. Most jobs need less: on M2 the other jobs peaked at 296 to 341 MiB, and on H5E01 at 407 to 639 MiB, `unfrackit-h12` the highest. After each job the pool reads the worker's peak during it (`VmHWM` in `/proc/<pid>/status`, reset before the job). When that peak passed the job's estimate, it becomes the estimate of every later job of the same wallet.

Admission. A job starts when a worker is free and its charge, the running jobs' charges and the idle workers' resident sizes fit the budget. A free worker is an idle one, or a new one in a free place: no more than `--workers` worker processes exist at once, counting those stopped and not yet exited. A job's charge is the larger of its estimate and the resident size of the idle worker it takes. Idle workers are stopped, largest first, when that makes a job fit. The pool takes jobs in the order they were handed to it. A job held for memory may be passed by later jobs that fit, but at most `--workers` times. After that nothing passes it, the running jobs end, and it starts, so no job waits forever. A rerun after a worker died goes first and is never passed. When nothing runs and a job alone exceeds the budget, it runs alone, and the log notes that the machine is short of memory.

Recycling. After its job, a worker is replaced when its resident size passes the budget divided by `--workers`, or when CSL's WebAssembly memory passes half its ceiling. The ceiling is the module's declared maximum, or 4 GiB, the limit of a 32-bit WebAssembly memory, when it declares none, as CSL 17.0.0 does. Otherwise, a worker is replaced after 40 jobs. A worker that recorded machine errors is replaced after its job.

Reruns. A worker that dies during a job runs the job again as "Workers and watchdogs" above describes: in a fresh worker with the estimate doubled, then alone with the whole budget. None of these rules changes a record: they change when and in which worker a job runs.

history/<wallet>.<window>.jsonl   one wallet and window
history-run.json                  the run's snapshot, parameters, settings, byte source, the draw's run-level counts and per-file counts
census.jsonl, census-run.json     the census rows and the run's summary

collateral.json                   the collateral measurement

Files name wallets by db-sync's stake-credential id (`stake_address.id`); no stake address appears in them.

#### A replay's run directory

The `replay` command writes a stage: each wallet's records whole, as a segment of their own. Several wallets run at once and are done in any order ("Workers and watchdogs" above), and the segments are joined in wallet order once every wallet is done. Under the same root:

```
wallets.json                     the ordered wallet list: { file, sha256 } per history file, in the order
                                 --history gives them (a directory's files sorted by name), or { shape } per
                                 shape, in the order --shapes gives them; a wallet's index is its position
run.json                         what decides the records and nothing about the machine: the stage layout, the
                                 command, the plan and its entries, the options that change a record, the
                                 settings, the treatment's digests, the code manifest, the Node version, the CSL
                                 build (package, version and the SHA-256 of each WebAssembly file) and
                                 walletsSha256, the SHA-256 of wallets.json
segments/<i>.records.jsonl.gz    wallet i's records, one gzip member at level 6
segments/<i>.timings.jsonl.gz    wallet i's timing rows, one gzip member at level 6
segments/<i>.done.json           written after both: for each file the SHA-256, bytes and lines of its
                                 decompressed bytes and its compressed size; the record counts by kind; the
                                 wallet's totals; the machine label; start and end; run.json's SHA-256
machines/<label>.json            one entry per invocation under the label: the host facts, physical cores,
                                 virtualization (wsl2, vm or none), the worker count, the memory budget
                                 (memoryBudgetBytes) and the pool's counts (pool), its share of the wallets
                                 (selection: null, the shard or the index file), the indexes it completed
                                 in the order it completed them, whether it reached the stage's end, start
                                 and end; a merge's entry also names the indexes it copied (merged)
machines/<label>.log.jsonl       the log, appended: open or resume (or a stage found ended), start, the
                                 window (worker count, queue target, jobs in the pool, cap on open
                                 wallets), each watchdog stop, machine rerun, error, wallet done and
                                 wallet run again with its reason, a shard's part or the stage's end, a
                                 merge, end
records.jsonl.gz                 at the stage's end: the segments' records joined in index order
timings.jsonl.gz                 at the stage's end: the segments' timing rows joined in index order
done.json                        written last: the joined streams' SHA-256, bytes, lines and compressed sizes,
                                 the record counts by kind and the totals, summed from the segments' done files
spool/<i>/                       while wallet i is open: its jobs' records and its segment before compression
lock                             the process ID of the invocation writing the stage
```

The options in `run.json` leave out `--workers`, `--machine`, `--shard`, `--wallet-indexes`, `--run-id`, `--treatment`, `--treatment-pins` and `--history`: they say how the run uses the machine, which of the wallets it runs or where its files are, and the treatment and the wallets are recorded by their content. The SHA-256 of `run.json` is the stage's compatibility key. The machine label is the operator's choice, and the stage records no host name or address apart from it.

A replay's records are built in the worker that ran the job, as the job ends, and written to the job's spool files under `spool/<wallet index>/`: the record lines exactly as the segment takes them, and their timing rows numbered within the job. The main thread commits the spools in job order to the wallet's segment as the jobs end, renumbering the timing rows to follow on and setting each `wallet-arm` row's time to the job's attempt as the pool measured it. The records are those that one thread writing every job in turn would write, whatever order the jobs end in. The main thread holds no wallet's records. Of each job it keeps whether it was refused and its validity summary. When the wallet's jobs have all completed, the segment's two files are compressed, each written under its name with `.tmp` added and renamed once complete, and the wallet's done file is written last, the same way. The compression runs on Node's thread pool and the writes are asynchronous, so the main thread goes on handing out the other wallets' jobs. A failed job or a stop point stops the run, and no further job starts. The wallets whose jobs had all completed finish closing and keep their segments. Every other open wallet is dropped without a done file, so only whole wallets are done.

Timing rows lead with the wallet's index, `walletIndex`, and number the records from 1 within the wallet's segment (`n`), so the segments' rows join without renumbering. The `n`-th record of wallet `i` is line `n` of its segment, and, in the joined stream, line `n` after the lines of the wallets before it (each done file's `records.lines`).

Resume. The same command on the same run ID resumes the stage. It compares `run.json` with this invocation's, field by field, and refuses any difference, naming the fields that differ; so a resume under another Node version or CSL build is refused. The worker count, the memory budget and the machine label are not in `run.json`, so any of them may change. Every wallet whose done file exists, names this `run.json` and whose segment files decompress to the SHA-256 and byte count it records is skipped. Every other wallet runs again: its files are deleted first (a temporary file, a segment with no done file, one whose bytes do not match, which the log notes with the reason), and so is the spool. A second invocation on a stage that a running process holds is refused; the lock of a process that has gone is taken over. A stage that has ended (its `done.json` names this `run.json` and the wallet count, and both joined files have the compressed sizes it records) is not resumed: the command runs nothing, changes no segment or joined file, logs `stage-ended-earlier`, adds its invocation to the machine record and prints the totals `done.json` holds, with `endedEarlier`.

The stage's end. When every wallet from 0 to N-1 has its done file, the segments' gzip members are joined in index order into `records.jsonl.gz` and `timings.jsonl.gz`, byte for byte, without recompression. The joined stream is decompressed and cut at the segments' byte counts, each part must give its segment's SHA-256, and `done.json` records the joined stream's own SHA-256. A wallet without a done file stops the stage's end before it writes anything. The segments are kept. The command's printout gives the totals and record counts summed from the done files, so a resumed run prints what an uninterrupted one does.

Identity is defined on the decompressed bytes: the decompressed `records.jsonl.gz` of a stage equals the `records.jsonl` one uninterrupted run writes, whatever the worker count, the machine or the stops and resumes. Compressed bytes can differ with the zlib version or how writes are chunked, which is no difference in results. A stream of several gzip members is a valid gzip file, read whole by `zcat records.jsonl.gz` or, in Node, by `createReadStream(path).pipe(zlib.createGunzip())`, which read every member.

Every record names its wallet (the stake-credential id, or a shape's name), window, arm, variant, method, change policy, collateral rule and repetition, and an intent by its position in the wallet's stream. A record that would carry an address, a stake address, a transaction hash or a credential is refused, and free-text fields (a failure's detail, a refusal's reason) have them replaced by placeholders. The kinds:

- `spend`: one replayed intent. Its outcome is one of: built; failed, with its class and a detail that names any part written after the library priced the transaction and any of the intent's redeemers the transaction lacks; infeasible by balance; infeasible for collateral, with its reason; not replayable; or forfeit. Not replayable means an intent the method has no way to express: the H-12 rule, the test method or `cjs-rrri` meets a body field the kit cannot replay, such as protocol parameter updates; a CSL method meets a part CSL cannot express; or `evo-lf` meets a part its library's types cannot hold. The record also holds the fee and the wallet-controlled fee, size, inputs, signing keys and assets dragged. For H-7's drift it holds the count of every wallet UTxO the spend consumes with the intent's fixed wallet inputs included (`consumedWalletInputs`; `inputs` leaves them out) and the largest Value among them (`largestConsumedValueBytes`). It holds the minimum coin of the token-carrying change outputs (`changeTokenMinimum`) and the minimum coin the consumed token-carrying wallet UTxOs would need without the tokens the spend sends away (`consumedTokenMinimum`). A requested token that no change output carries is sent away, a token only partly sent stays, and a UTxO left with no token adds nothing. Both minimums are lovelace, written as decimal strings. It also holds the change outputs with their bytes and largest Value; the drag bytes; the bytes and fee per policy recreated in change; the collateral used (`chosen`: `set-aside`, or `library` for the Evolution SDK's methods); and the collateral available under every rule at a script interaction. For a built spend and for a forfeit it holds the state after it, every UTxO it holds counted, held ones included: the UTxO count (`utxosAfter`), the largest Value (`largestValueBytesAfter`), the locked ADA (`lockedAdaAfter`), the locked ADA per token (`lockedAdaPerTokenAfter`, `null` when no token is held) and the number of distinct tokens held (`tokensAfter`);
- `burst`: a parallel burst's separate pass, and whether it was feasible;
- `wallet-arm`: per wallet and arm over the window: counts by outcome and class, the held UTxOs that held-consumed events removed (`heldConsumed`) and those they named that the arm did not hold, because the spend that created them was not built in it (`heldMissing`), the held outputs of built spends that matched no requested output (`heldUnmatched`, expected 0), failures per 100 attempted spends, spend, wallet-controlled, plan (always 0: no arm plans) and forfeit fees, burst feasibility, the start state (`start`, at time 0: the state the trajectory begins from) and the end state (`end`; `capped` is true when the wallet's history ended at its 1,000th window transaction, so that the end state is the state after that transaction and not the window's end), each with its UTxO count, largest Value, locked ADA, locked ADA per token and token count, the largest Value's trajectory (one point for the start and one for each built spend, forfeit and spend infeasible for collateral, in order; a spend infeasible for collateral carries no state after it, and its point repeats the previous one), the end state's conformity to the treatment's layout (`conformity`, below), `triggers` (always 0) and `policies` (always null), and, under `--validity`, the `validity` counts (below);
- `refused`: a replay the rules do not settle (a wallet for which the change-address rule names no address where the replay needs one).

The `fidelity` command writes `run.json` and `fidelity.json`, its counts and distributions per window, under the private root.

The `live-fire` command writes its stages under `<network>/<run-id>/<stage>/`, as a study does, and deletes `<network>/<run-id>/` when the run ends, unless a failed run is kept for debugging. Its entries go to the extraction tool's check log ("Live-fire checks" below).

The `study` command writes under `<network>/<run-id>/`, where the network is `--expect-network`, or `synthetic`:

```
study.json   the plan, its stages, the options with paths made absolute as the first start gave them (the worker
             counts, the memory budget, the machine label, the share of the wallets and the stop stage left
             out), the SHA-256 of the treatment pins, wallets and extraction-run files, the code manifest (as
             hash prints it) and its SHA-256, the Node version
log.jsonl    appended: each invocation's start or resume with its worker counts, machine label, share of the
             wallets, stop stage and machine record, each stage's start, then its end with the stage's printout
             (and, for a stage that is not a replay, its outputs: the file count, the bytes and a SHA-256 over
             every file of its directory), a shard's part, or its error; the stages skipped; a stop; the end,
             with the stages not ended
lock         the process ID of the invocation running it
<stage>/     each stage's own run directory, written by its command under the run ID <run-id>/<stage>
```

#### A replay split across machines

A replay stage's wallets can be split between machines. Each machine writes whole wallets as segments, and `merge-stage` joins them in wallet order into the stage one uninterrupted run writes. Which wallets an invocation runs is its share. Like `--workers`, the share changes no record: it is not in `run.json`, so every shard of a stage has the same compatibility key, and the invocation's entry in `machines/<label>.json` records it (`selection`).

- `--shard <k>/<n>` runs the wallets whose index modulo n is k, with 0 <= k < n.
- `--wallet-indexes <file>` runs the indexes that a `plan-shards` file holds for the replay's plan. The file must have been planned for this stage's wallet list, its count and the SHA-256 of `wallets.json`.

A shard runs only its wallets that are not done, then ends without the stage's join. Its printout gives `ended: false` and `shard`: the share, the done indexes as ranges (such as `0-3,5`), their count and how many remain; the log gets a `stage-part` entry. When every index happens to be done in its directory, the stage ends as an unsharded one does. A stopped shard resumes as any stage does.

`plan-shards` writes one wallet index file per machine, `<out>/<label>.json`. Each holds the format, the machine, the machines and their speeds, the cost formula, and per plan the wallet count, the SHA-256 of the wallet list, the indexes, the machine's cost, its share of the total cost and its balance (its estimated time over the ideal, where 1 is even). The estimate per wallet is deterministic:

```
cost = (E + 1) × J × g × √g,   g = 1 + U / 1000
```

E is the window's event count: the history file's end record, or a shape's synthetic stream. J is the wallet's job count under the plan. U is the larger of the UTxO counts at the window's start (the state record) and end (the end record); for a shape, the count at its start. For large U, g × √g grows as U^1.5, faster than linearly. The measured replay time per event rose about 15 times from 3,005 to 20,005 UTxOs, while g × √g rises about 12 times over that range, so the formula understates the growth. The wallets are taken in falling cost (ties by index), and each goes to the machine that would finish it first at its relative speed (`--machines spare=1,laptop=0.6`; a machine without `=` has speed 1; ties go to the machine named first). The assignment changes only how long each machine runs, never a record. A file already in `--out` for the same machines and speeds gains the plan's entry, so one file per machine serves a study's two replay stages, whose wallet lists differ.

`merge-stage --into <dir> [--machine <label>] <source dir>...` joins the shards of one stage. The target is a stage's directory, or a new or empty one, which takes the sources' `run.json` and `wallets.json`. Before it writes anything, the merge reads every place (the target and each source) and checks every segment, and it is refused when:

- a place's `run.json` or `wallets.json` differs from the target's (or the first source's), naming the fields `run.json` differs in, or a place's `wallets.json` is not the one its `run.json` names;
- a running process holds a source, or a source has no `run.json`;
- a segment fails the resume's check: its done file must name this `run.json` and its index, and both files must decompress to the SHA-256 and byte count it records;
- a wallet index is in two places with different decompressed records or timing rows. The timing rows of two runs always differ, and so do an unseeded selector's records, so two runs of one wallet never merge: the message names the index and both places, and the operator deletes one copy's three files and merges again;
- some index from 0 to N-1 is in no place;
- a machine record (`machines/<label>.json` or `<label>.log.jsonl`) is in two places with different contents, or the merge's own label names a record only a source has: each machine runs under a label of its own.

Then the target gains the segments and machine records it lacks, copied (each file under a temporary name, flushed and renamed, the done file last), and the stage's end runs: the segments joined in index order and checked against their done files, `done.json` written last. The merge is recorded under its own label (`--machine`, `local` when absent): an invocation with `command: "merge-stage"` and the indexes it copied, and `stage-merge` and `stage-end` log entries. The sources are only read. The printout gives the wallets, how many the target kept, how many it copied, the equal copies set aside (`duplicates`), and the totals and record counts. A replay or study run again on the merged stage finds it ended.

#### Validity checks

`--validity` reads every transaction a method or plan returns and the kit passes with cardano-serialization-lib, and runs the four negative controls on it. CSL's re-serialization must have the transaction's inputs, fee and witness count and its outputs by decoded content. CSL writes a policy's asset names shortest first and re-encodes some fixed parts (certificates, witness lists) as tagged sets, so an output's bytes or the transaction's hash can differ. Both are counted (`cslOutputBytes`, `cslReencoded`) and neither is a failure. The controls (`src/kit/controls.mjs`, which the tests import through `test/lib/controls.mjs`) are the fee one lovelace under the ledger minimum with the difference moved into the last output, the size one byte over the limit, a Value one byte over the value-size limit, and one vkey witness short; each must be caught by its own check alone. A transaction can have no outputs: a library burns a leftover below the change minimum into the fee, and the intent requests nothing. It has no output to take the fee difference and none whose Value could be too large, so it has no fee or value control and is counted in `notApplicable`.

A replay's `wallet-arm` record gains `validity: { txs, cslRead, cslOutputBytes, cslReencoded, controls: { fee, size, value, witnesses }, notApplicable: { fee, value }, failed }`, with `controls` counting the transactions each control was caught on and `cslRead` those CSL read and re-serialized to the same inputs, fee, witness count and outputs. A replay counts the transactions of its spends and of the burst pass. A failure adds `failures` (up to 20 entries: where it came from, the transaction's position in the answer, the check and a scrubbed detail, never a hash). It writes a `validity failure` note for each failure it details, and a `validity failures not detailed` note with the count of the rest, to the run's log (`log.jsonl`, or a replay stage's `machines/<label>.log.jsonl`), and makes the command exit with status 1 after it has printed its totals, which carry the sums. The option adds no other field and changes none (`test/treatment/validity.test.mjs`).

### History files

One JSON Lines file per wallet and window. Amounts are decimal strings; hashes, policies, names and CBOR lowercase hex; references `<transaction id>#<index>`.

1. `header`: the wallet, frame and split; `sample`, the wallet's membership as `{ recentRandom, peakRandom, recentStratum }`: each frame's random sample and the recent frame's purposive strata (null when the study tables were not read or the wallet is in no sample); `draw`, the extraction's fields for the wallet and this frame, as `{ sizeGroup, nWindowTx, capped, historyHi }` from `study.sample` (`size_group` B0 to B3, `n_window_tx`, `capped`, `history_hi`; null when the study tables were not read, the frame is not the extraction's recent or peak window, or the wallet is not in that frame's sample); the window's first and last blocks, its transaction-id range [`lo`, `hi`], the transaction id of its start state and `endTime`, the block time at which the replay ends; the snapshot; the snapshot epoch's protocol parameters; the franken-flagged payment credentials; the arrival table; `latestKeyBase`, the latest output the wallet received at or before the start state's transaction, spent or not, at a key payment credential and a base address whose credential is not franken-flagged, as `{ address, txId, index }` (null when there is none); the settings; the byte source and db-sync version.
2. `state`: the UTxO set as of the last block before the window's first block, as UTxO records.
3. Events in chain order:
   - `deposit`: the wallet outputs created by a transaction that is not the wallet's spend, as UTxO records;
   - `held-consumed`: the held wallet UTxOs consumed by a transaction that is not the wallet's spend;
   - `intent`: a spend and its intent;
   - `self-reorganization`: a spend with no requested output, no certificate, vote or proposal, no mint or burn and no script; counted, its reshuffle of the wallet's inputs not replayed. It carries its implicit values, the held UTxOs it consumed, `withdrawal` (its reward withdrawals, which the replay deposits), the net value it brought in from outside the wallet other than those, and the observed wallet parts;
   - `mark`: every 30 days of block time from the window's first block, placed before the first event at or after its time.
4. `end`: the UTxO set's count and digest at the end of the replayed history, `capped`, and the event counts.

The window cap. A wallet whose `draw.capped` is true has more window transactions than the extraction's history cap (1,000), counted as the extraction counts them: the distinct window transactions that create or consume an output of the wallet, in transaction-id order. Its history covers the window's `lo` to `draw.historyHi`, the id of its 1,000th such transaction. In its file `window.hi` is `historyHi`, `window.endTime` is the block time of that transaction, and no event follows it. The `end` record is the state after it (`at.tx` is `historyHi`) and says `capped: true`. The replay reads that as the end state of a capped wallet (the `wallet-arm` record's `capped`). The start state at `window.tStart` is read as for every wallet. An uncapped wallet's history is unchanged: `window.hi` is the window's last transaction, equal to its `historyHi`, and `capped` is false. `history` checks each wallet against the extraction before writing its file: the window's transaction count must equal `nWindowTx`, `capped` must equal `nWindowTx` above the cap, an uncapped wallet's `historyHi` must be the window's `hi`, and a capped wallet's 1,000th window transaction must be `historyHi`. A wallet that fails a check stops the command with the difference.

The extraction's draw. `history-run.json` holds `draw`, null when the study tables were not read, and otherwise per frame (`recent`, `peak`): `quotaScale` (the extraction's `quota_scale`, s, as decimal text), `sampleN`, `historyCap` and `groups`, per size group B0 to B3 `{ quota, nDrawn, nTaken }` from `study.draw_group` (`quota`, null for B0; `nDrawn`, D_k, the candidates drawn into the group; `nTaken`, A_k, those taken). The record holds the counts only: the weight D_k / A_k is the analysis's to compute. `history` refuses, saying to rerun the extraction at e861aa0 or later, when the extraction run lacks `study.sample`'s `size_group`, `n_window_tx`, `capped` and `history_hi`, or `study.draw_group`, or `study.draw_summary`'s `quota_scale`, `sample_n` and `history_cap`.

A UTxO record is `{ ref, cbor, address, cred, coin, assets, held, origin, txId }`: `cbor` is the CIP-30 `TransactionUnspentOutput` (CIP-0030, "TransactionUnspentOutput": `[input, output]`), `cred` the payment credential, `assets` `[{ policy, name, qty }]` sorted by policy then name bytes, `held` the reason the UTxO is held (`script-payment`, `datum`, `reference-script` or `franken`) or null, `origin` `initial` or `deposit`, and `txId` db-sync's id of the creating transaction, which follows chain order and ranks outputs for the change address. The output inside `cbor` is re-encoded from db-sync's columns on every network, so that preprod runs the code mainnet runs. The address bytes come from its text and the value takes the ledger's serialization. A datum is its hash or the inline datum's bytes. A reference script comes from db-sync's script bytes, or, for a native script, whose bytes db-sync does not keep, from its creating transaction's bytes. db-sync does not record whether the original output used the array or the map form, so the re-encoding uses the map form only when an inline datum or a reference script needs it; its content always equals the original's.

An intent is `{ id, source, type, time, requested, implicit, fixed, collateral, invalid, burst, observed, classes, derived }`:

- `time`: slot, block time (Unix seconds), index in the block, epoch, block number.
- `requested`: `[{ cbor, address, coin, assets, datum, scriptRef, raised, index, wallet, scriptPayment }]`, with `from` and `inflow` on a requested wallet output built from an inflow. `raised` is null or `{ from, to, rule, original }`.
- `implicit`: `{ withdrawals, refunds, deposits, donation, mint, burn }`.
- `fixed`: null, or `{ inputs, referenceInputs, body, witnesses, redeemers, auxiliaryData, scriptFee, fixedBytes, refScriptBytes }`. `inputs` and `referenceInputs` are `[{ ref, cbor }]`, a held wallet input carrying `held` and, at a key payment credential, `walletKey`; `body` maps Conway CDDL body field numbers to CBOR; `witnesses` maps witness-set keys to CBOR; a redeemer is `{ tag, target, data, exUnits }`.
- `collateral`: `{ required, observed }`, `observed` null or `{ inputs, return, total }`.
- `invalid`: null, or for a phase-2-invalid transaction `{ forfeit, heldConsumed }`.
- `burst`: null or `{ id, parallel, index }`.
- `observed`: `{ tx, size, fee, epoch, protocolMajor, minFeeA, minFeeB, walletInputs, walletOutputs, walletWitnesses }`.
- `classes`: each asset of the transaction's wallet inputs, outputs and requested outputs, `FT` or `NFT`.
- `derived`: null, or the pool deposits taken from db-sync's net deposit.

## The study run

`study` runs the commands above as one chain under one run ID, each stage in its own run directory, so that a run of many hours can stop and resume. Three plans:

| Plan | Stages, in order | Wallets, snapshot and windows |
|---|---|---|
| `synthetic` | `replay-recent`, `replay-peak` | The shapes `--shapes` names, with their synthetic streams. No database, so no collateral measurement: `--collateral-rule ledger\|practice` is required. |
| `preprod` | `history-recent`, `history-peak`, `census`, `near-cap`, `collateral`, `fidelity`, `replay-recent`, `replay-peak` | A test network (`--expect-network`, never mainnet). The wallets from `--wallets`, `--wallet` or `--from-study random\|all`. The snapshot from `--snapshot <block id or hash>` or `--extraction-run`, never the tip, so that every stage reads one block. The windows from `--extraction-run`, or computed from the snapshot. `--days` for the collateral measurement. |
| `corpus` | as `preprod` | Every sampled wallet (`--from-study all`), with `--analysis-freeze-tx` required, since the confirmation split is read. The snapshot and windows are the extraction run's: on mainnet the gate's, on a test network `--extraction-run`'s. |

Each stage runs one command:

- `history-recent` and `history-peak`: `history` for that window;
- `census` and `near-cap` over the wallets given, or with `--from-study` for the corpus (the census over the recent frame's eligible wallets, near-cap over both random samples); `collateral`;
- `fidelity`: over the recent and peak history files of the exploration split, and those that carry no split, as on a test network;
- `replay-recent` and `replay-peak`: `replay --plan recent` and `--plan peak` over that window's history files, or over the shapes' streams, under the study's collateral rule, with the validity checks on every job.


The collateral rule. Every replay job runs under one rule. In the `preprod` and `corpus` plans it is the pick from the `collateral` stage's report: practice when more than half of the recent window's script-executing transactions whose collateral inputs all sit at key addresses carry less than 20 ADA of collateral in total, otherwise ledger. The study reads `collateral.json` when the first replay stage starts (a resumed run reads it again), refuses to go on when the measurement found no such transaction, logs a `collateral-rule` entry, and records the rule, its source, the share and the number of transactions measured in `study.json` under `collateralRule` (the header's other fields are fixed at the start; this one is filled in then and is not compared on resume). In the `synthetic` plan the rule is `--collateral-rule`, recorded as `{ rule, source }`. The other rules stay as recorded availability at each script spend and forfeit.
The database stages come first, so a run needs the database only at its start. `--reps` (the repetitions of a library that picks at random, 10 when absent), `--workers`, `--memory-budget`, `--machine`, `--shard` and `--wallet-indexes` pass to the replays, which always run with the validity checks; `--analysis-freeze-tx` to `history` and the replays; `--treatment` and `--treatment-pins` (default `data/treatment-pins.txt`) to every stage that loads the treatment; the connection's options (`--expect-network`, `--snapshot`, `--extraction-run`, `--bytes`, `--immutable-dir`, `--immutable-host`, `--set`) to every database stage. An option the plan does not use is refused before any stage starts, and so is a worker count that is not a positive whole number, a memory budget that is not a positive number of GiB, a machine label that is not one, a shard that is not k/n with 0 <= k < n, `--shard` given with `--wallet-indexes`, and a `--stop-before` that names no stage of the plan.

Running the same plan and run ID again resumes the run. Its options, the SHA-256 of its input files and the code manifest must equal those of its first start, or it is refused, naming what differs. The worker count, the memory budget, the machine label, the share of the wallets and the stop stage are not compared: they change no record, so a resume may use others, on this machine or another. Nor are the paths that `--treatment`, `--treatment-pins`, `--wallets`, `--extraction-run` and `--immutable-dir` name. The files are compared by content instead, through the SHA-256 of the treatment pins, the wallets file and the extraction run's file, so on another machine they may sit at other paths. The pins cover every treatment file, and a stage refuses a treatment that does not match them. A file with other content is refused, naming it. The ImmutableDB directory is not hashed, since the node keeps appending to it: each block read from it is found by the hash and slot the database gives and checked against its chunk index's CRC-32. A resume keeps the header its first start wrote, filling in only the collateral rule. A stage whose end entry is in the log is skipped. A replay stage that has not ended resumes at the wallets it has not done, keeping the done wallets' segments ("A replay's run directory" above). Every other stage reruns from its start, its directory removed first, so its files are written as by an uninterrupted run, and a stage stopped halfway loses its partial work. The records then equal an uninterrupted run's, except where a stage's records vary between any two runs: the unseeded selector (`csl-ri`). A second invocation on a run ID that is running is refused; the lock of a process that has gone is taken over. A stage that throws stops the run, with its error in the log. A stage that finishes with a failed validity check is logged as failed, the run goes on, and the command exits with status 1 at the end.

The study's mainnet run, after the final freeze:

```
node src/cli.mjs study --plan corpus --run-id <id> --expect-network mainnet \
  --treatment <dir> --treatment-pins data/treatment-pins.txt \
  --analysis-freeze-tx <hash> \
  --immutable-dir <the node's ImmutableDB directory> --immutable-host <host> \
  --workers 8
```

It runs at the study's repetitions (the plan's defaults), every replay to completion. Its 8 replay workers suit the workstation; another machine may use another count, which changes no record. Its connection (`PGHOST` and the rest) is mainnet's db-sync, through a role that can read the `study` schema.

### The study split across machines

The replay stages can be split between machines; every other stage runs once, on the machine that reaches the database. Each machine writes whole wallets, and `merge-stage` joins them into the stages one machine would have written ("A replay split across machines" above). Every machine runs the same commit installed with `npm ci`, the same Node version, and the same treatment, pins and input files, at whatever paths. A replay stage's `run.json` pins the code manifest, the Node version, the CSL build and the treatment's digests, and `merge-stage` refuses shards whose `run.json` differ.

1. On the machine that reaches the database, run the stages before the replays, and stop:

   ```
   node src/cli.mjs study --plan corpus --run-id <id> <options> --stop-before replay-recent
   ```

   Each of these stages' end entries in `log.jsonl` records its outputs: the file count, the bytes and a SHA-256 over every file of its directory.
2. To split by estimated cost rather than by index, plan each window, with the study's `--reps` and the rule `collateral.json` gives (`collateralRule`). Both commands write into the same file per machine:

   ```
   node src/cli.mjs plan-shards --plan recent --history <root>/<network>/<id>/history-recent/history \
     --collateral-rule <rule> --reps <n> --machines spare=1,laptop=0.6 --out <dir>
   node src/cli.mjs plan-shards --plan peak --history <root>/<network>/<id>/history-peak/history \
     --collateral-rule <rule> --reps <n> --machines spare=1,laptop=0.6 --out <dir>
   ```
3. Copy the run's directory, `<root>/<network>/<id>/` (`study.json`, `log.jsonl` and the stages' directories), to the same place under each other machine's root, with that machine's index file if step 2 made one.
4. On each machine, run the study with the same options, the machine's share and a label of its own. The path options may name other paths there, provided the files hold the same content:

   ```
   node src/cli.mjs study <the same options> --shard 0/2 --machine spare
   node src/cli.mjs study <the same options> --shard 1/2 --machine laptop
   ```

   or `--wallet-indexes <dir>/spare.json` and `--wallet-indexes <dir>/laptop.json`. A sharded study runs only the replay stages. It reads the collateral rule from the copied `collateral.json`, runs its share of `replay-recent` and then of `replay-peak`, and logs each as `stage-part`, not ended; its end entry lists both as not ended. Run again, it resumes at its wallets not done.
5. Copy each replay stage's directory from every other machine to the first machine, outside the run's directory, and merge them into the run's stages:

   ```
   node src/cli.mjs merge-stage --into <root>/<network>/<id>/replay-recent --machine spare <copy>/replay-recent
   node src/cli.mjs merge-stage --into <root>/<network>/<id>/replay-peak --machine spare <copy>/replay-peak
   ```
6. Run the study again on the first machine, with the same options and no share. It finds both replay stages ended (their `done.json` valid), logs their ends without running a wallet, and ends. The check: each merge's printout counts every wallet (`kept` plus `copied` equals `wallets`), and the study's printout gives `unfinished: []` and both replay stages with `ended: true`.

A synthetic plan has no stage before its replays and takes its collateral rule from `--collateral-rule`, so each machine starts its shard with no copy (step 4), and steps 5 and 6 follow.

The refusals. A sharded study is refused before anything is written when a stage other than the replays has no end entry in the log ("run the stages before the replays where the database is reachable"), when an end entry records no outputs (a log written before outputs were recorded), and when a stage's directory does not hold the outputs its end recorded, naming the stage with the recorded and present file counts and bytes. The replay refuses an index file it cannot read, one that is not a `plan-shards` file, one with no entry for its plan, one planned for another wallet list, and one whose indexes are not increasing indexes below the wallet count. `plan-shards` refuses a `--machines` entry that is not `<label>` or `<label>=<positive number>`, a label given twice, a file in `--out` planned for other machines, and the shapes without `--treatment`. `merge-stage`'s refusals are listed under "A replay split across machines" above.

## Running jobs unattended

`scripts/run-queue.mjs` runs a list of commands one after another without anyone watching, and records what happened so that a stopped list resumes where it left off. It runs commands and nothing else: the simulator's own commands check their options, and the runner adds nothing of its own beyond a wall-clock limit per job. It uses only Node's built-ins.

No outcome depends on what else the machine is doing, but the times do. Keep a long run whose timings matter the only load on the machine. A job's `idle` setting makes the runner wait until the one-minute load average has stayed low before it starts the job, and fail the job if that does not happen in time.

A queue is a JSON file. This one runs a recent-plan replay and then a peak-plan replay on the synthetic shapes, with the output location in an env file:

```
{
  "name": "synthetic-check",
  "out": "queue-out",
  "envFile": "run.env",
  "jobs": [
    {
      "id": "replay",
      "cwd": "/path/to/research-sim",
      "argv": ["node", "src/cli.mjs", "replay", "--treatment", "/path/to/treatment", "--shapes", "all", "--plan", "recent", "--collateral-rule", "ledger", "--run-id", "synthetic-replay", "--workers", "2"],
      "timeoutMinutes": 120,
      "idle": { "maxLoad1": 1.0, "forMinutes": 5, "maxWaitMinutes": 60 },
      "pauseAfter": true
    },
    {
      "id": "peak",
      "cwd": "/path/to/research-sim",
      "argv": ["node", "src/cli.mjs", "replay", "--treatment", "/path/to/treatment", "--shapes", "all", "--plan", "peak", "--collateral-rule", "ledger", "--run-id", "synthetic-peak", "--workers", "2"],
      "timeoutMinutes": 120
    }
  ]
}
```

`run.env` holds lines such as `export RESEARCH_SIM_HOME=/path/to/output`. A relative `out`, `cwd` or `envFile` is resolved against the queue file's directory.

The queue file is checked whole before anything runs. An unknown key, a missing or mistyped field, a duplicate id, a `cwd` that does not exist and a timeout that is not positive are refused with the path of the field, and nothing runs. The top level has `name`, `out` (the directory for the state file and logs), `jobs` and optionally `env` and `envFile`, which apply to every job. A job has:

| Field | Meaning |
|---|---|
| `id` | A safe file name, unique in the queue. The job's logs go under `out/<id>/`. |
| `cwd` | The directory the job runs in. |
| `argv` | The command and its arguments, as an array. No shell is involved. |
| `timeoutMinutes` | Required. The job's wall-clock limit. |
| `env`, `envFile` | Environment for this job. |
| `idle` | `maxLoad1`, `forMinutes` and `maxWaitMinutes`, all required: wait until the one-minute load average has stayed at or under `maxLoad1` for `forMinutes`, and fail the job if that has not happened within `maxWaitMinutes`. |
| `before`, `after` | Commands (argv arrays) run in the job's directory and environment, each under the job's limit. `before` must exit 0, or the job fails without running. `after` runs once the job has started or failed, whatever the outcome, and its exit status is recorded without changing the job's status. A runner stopped by a signal does not run it. |
| `pauseAfter` | Stop the queue once this job is done. |

An env file holds lines `KEY=VALUE` or `export KEY=VALUE`, comments starting with `#`, and blank lines. A value is everything after the first `=`, taken literally: no quotes are interpreted and nothing is expanded. Any other line is refused. A job's variables override the queue's, and both override the environment the runner inherited; within one level, `env` overrides `envFile`.

```
node scripts/run-queue.mjs run <queue.json> [--continue-on-failure] [--rerun-interrupted] [--detach]
node scripts/run-queue.mjs status <queue.json>
```

`run` takes a lock file in `out`, holding the runner's process ID, so that one runner serves a queue: it is refused while that process lives and taken over, with a message, when the process is gone. Jobs run in order, one at a time, each in its own process group with standard output and standard error in `out/<id>/attempt-<n>/stdout.log` and `stderr.log` (`before.log` and `after.log` beside them). When a job passes its limit, the whole group receives SIGTERM and, if anything is left 30 seconds later, SIGKILL, and the job is `timeout`. A non-zero exit or a signal makes it `failed`. The queue stops at the first job that is not done, unless `--continue-on-failure` is given.

To resume, run the same command again. A job recorded `done` is skipped; a `failed` or `timeout` job runs again as a new attempt. `--detach` starts the runner in a new session with its output in `out/runner.log`, prints its process ID and returns. `status` prints one line per job (id, status, attempts, last duration and exit) and whether a runner holds the lock.

SIGINT or SIGTERM to the runner is passed to the running job's group, the job is recorded `interrupted` and the lock is released. A job recorded as running whose process is gone (the runner was killed, or the machine restarted) is marked `interrupted` the next time the runner starts, and the runner refuses to go on until it is started with `--rerun-interrupted`, which runs the job again as a new attempt. The choice is left to the operator because a rerun can meet a half-written run directory; look at it first. If an interrupted job's process is still alive, the runner refuses to start.

Exit codes of `run`:

| Code | Meaning |
|---|---|
| 0 | Every job is done. |
| 1 | A job failed or timed out. |
| 2 | The queue is invalid, or another runner holds the lock. |
| 3 | The queue paused after a `pauseAfter` job, with jobs left. |
| 4 | An interrupted job awaits `--rerun-interrupted`, or a signal interrupted a job. |

`out/state.json` is rewritten atomically (a temporary file renamed over it) at every transition, so it can be read while the queue runs. For each job it holds the status (`pending`, `waiting-idle`, `running`, `done`, `failed`, `timeout` or `interrupted`) and, for each attempt, the start and end times, the duration, the exit code or signal, the process ID, the load average at the start, the exit status of `before` and `after`, the command and the names (never the values) of the variables set from the queue. For each runner start it records the CPU model, logical core count, total memory, operating system and Node version, and, for each job directory inside a git work tree, the commit and whether tracked files had uncommitted changes or untracked files were present, so that a reader comparing timings knows what produced them.

### The heavy probe

`scripts/heavy-probe.sh <queue dir>` measures the memory and the time of a replay on the heavy wallets. Its twelve jobs are `H20E01`, `H3E6` and `H20E05` under four job kinds, all on the observed arm (`csl-lf`, `cjs-rrri`, `evo-lf` and `csl-ri`), each in one process under `/usr/bin/time -v`, cheapest first. `H20E01` and `H20E05` differ only in events, which gives the event term at 20,000 UTxOs, and `H3E6` has about a seventh of the UTxOs and twelve times the events of `H20E05`, which together with them separates the UTxO term from the event term. Each job prints one JSON line per method answer, with the process's resident size, CSL's WebAssembly memory, V8's heap and external memory and the time since the replay began, and ends with a RESULT line. The script runs the queue with `--continue-on-failure`, logs the load average and available memory every minute, and writes a table with one row per job (wall time, maximum resident size, exit status, peak CSL memory, peak V8 heap, builds, intents built, intents failed). `node scripts/heavy-probe.mjs queue --dir <queue dir> --snapshot <simulator directory> --env <env file>` writes the queue; `scripts/heavy-probe.sh <queue dir> --resume` continues a stopped probe. A job that passes its cap (90 minutes for `H20E01`, 360 for the others) is stopped and the probe goes on. The machine should otherwise be idle.

## Live-fire checks

Before the final freeze, the study's code may run on mainnet wallets to confirm that it works, under a commitment that nothing such a run shows changes the pre-registration. The extraction tool's live-fire run with `--sim-wallets` picks the wallets from its draw order under a stated test value of h, at most ten, and keeps the pick in `sim/wallets.json` in its run directory until its own `cleanup`. On mainnet it picks once. The simulator's live-fire runs use that pick:

```
live-fire --run-id sim-<id> --extraction-run <id> --purpose <text> --expect-network <name>
          --treatment <dir> [--treatment-pins <file>] [--workers <n>]
          [--bytes tx_cbor|immutable] [--immutable-dir <dir>] [--immutable-host <host>] [--keep-for-debug]
live-fire --cleanup --run-id sim-<id> --network <name>
```

`--extraction-run` here names the extraction live-fire run by its run ID, not a `params.json` file. The run ID begins with `sim-`, so that neither tool's entries settle the other's runs. `--workers` (default 1) takes any positive whole number. Any option the command does not define is refused, and so is an option given twice. The pick fixes the snapshot block and the test value of h, so no option names them.

A run goes in this order:

1. The options, then the pick, checked as the gate's live-fire path checks it, against the check log of `--expect-network`. A refusal here has queried nothing and adds nothing to the log.
2. The gate, logged as a query: a `query-start` entry named `sim live-fire gate`, then a connection that reads db-sync's `meta`, refuses a database other than `--expect-network` and on mainnet takes the gate's live-fire path, then a `query` entry with its outcome. A refused gate is a failed query, never a live-fire run.
3. The `sim-live-fire-start` entry, written only after the gate has passed and before any wallet is read: the run ID, the gate's entry, the command line, the purpose, the test value of h, the extraction run, the code (the SHA-256 of the code manifest and the Node version), and the plan (the stages, the repetitions, the watchdog, the workers).
4. The stages, in the study's layout: each in its own run directory, `<run-id>/<stage>`, run by the command the study runs for it. `history-recent` and `history-peak` read every picked wallet at the pick's snapshot block, with the windows computed from that block. `replay-recent` and `replay-peak` run their window's plan. Validity checks are on throughout. Each random selector runs one repetition, and every replay runs under the ledger collateral rule, since no collateral measurement runs in a live-fire check. Every replay runs to completion, under the study's watchdog (a day per replay). A stage that throws stops the run. A stage that finishes with a failed validity check is a failed step, and the run goes on.
5. The `sim-live-fire` end entry, naming the start entry by `start_seq`.

The end entry holds the outcome (`succeeded` or `failed`), the error, the run time, and each step's name, outcome, class of error and time. A class of error is `refusal`, `history-check` (the history reader's checks of a wallet's transactions, its intents and its reconstruction), `database`, `connection`, `check` (a failed validity check) or the error's kind. It also holds three checks over the whole run, never per wallet. Each is true or false, or null when the stages that settle it did not all finish:

- `every_intent_parsed`: every history stage finished, so every spend in both windows became its event and every history file was completed. It is false when a history stage stopped on one of the reader's checks.
- `every_built_transaction_passed_ledger_checks`: no replay stage counted a validity failure. Every transaction a method or plan built and the kit passed was then read by CSL to the same inputs, fee, witness count and outputs, and each of its four negative controls was caught by its own check.
- `work_set_aside`: a watchdog stopped a replay, which then ran again to completion. It is read from the replay stages' pool counts.

The entry records no fee, size, count of failures or other outcome, and no stake address, address, policy or transaction hash. The error text passes through the extraction tool's redaction, applied in full to every error, this code's own refusals included: bech32 strings and long hex runs become `<bech32>` and `<hex>`, and every number becomes `#`. The progress lines name steps and times only, and the command prints the outcome, the steps, the checks and the log entries' numbers, nothing counted.

The last field, `wallet_level_output`, says what became of the run's directory: its history files, records and logs. The command deletes it when the run ends, whether the run succeeded or failed (`deleted <time>`, or `deletion failed: <error>`, or `none written`). With `--keep-for-debug`, a run in which a step failed keeps it instead (`kept for debugging`); a run that succeeds keeps nothing. Only the failed step's output is then read, to debug it, and once the fix is committed, `live-fire --cleanup --run-id <id> --network <name>` deletes the directory and adds a `cleanup` entry under the run's ID, with the fields the extraction tool's `cleanup` writes. A run killed midway leaves its start entry unclosed and its directory behind; the extraction tool's `check-log verify` reports it until the same run ID ends with its output deleted or `--cleanup` runs, which closes the start. The extraction run's `sim/wallets.json` is the extraction tool's, and only its `cleanup` deletes it.

The entries go to `check-log/<network>.jsonl` under the extraction tool's root, `RESEARCH_CORPUS_HOME` or `${XDG_DATA_HOME:-$HOME/.local/share}/unfrackit-research`, in that tool's format: one JSON object per line, appended, each with its sequence number and the SHA-256 of the file before it (`src/study/checklog.mjs`). The extraction tool reads them as live-fire runs: its final-freeze check takes the first live-fire start of either tool as the first live-fire run, which must follow the hypotheses record's block. Two runs appending to one log at once could write the same sequence number, so the live-fire runs and the extraction tool's commands run one at a time.

The mainnet run is the study author's, made by hand only after the hypotheses record is on chain and the extraction's mainnet live-fire run has picked the wallets:

```
node src/cli.mjs live-fire --run-id sim-<id> --extraction-run <the extraction run that picked> \
  --purpose <text> --expect-network mainnet \
  --treatment <dir> --treatment-pins data/treatment-pins.txt \
  --immutable-dir <the node's ImmutableDB directory> --immutable-host <host> \
  --workers 8
```

Its connection is mainnet's db-sync, through a role that can read `study.run` and `study.param`, and the run reads transaction bytes from the node's ImmutableDB, as the study does. On preprod the same command runs with `--expect-network preprod`, against preprod's check log and an extraction live-fire run on preprod.

## The rules this code implements

A wallet is a stake credential. Its outputs are those db-sync gives its `stake_address_id`: outputs at base addresses with its stake credential, whatever their payment credential, and outputs at pointer addresses created before Conway (CIP-0019, "Delegation part" and "Pointers"). Byron outputs never belong to a wallet. A wallet's UTxO set at transaction id T is every output created at or before T and not consumed at or before T, read from the wallet's own rows. Before a wallet is read, that set at the snapshot is compared with db-sync's own UTxO-at-block pattern restricted to the wallet, and a wallet whose two sets differ is refused.

Held UTxOs are kept and flagged, never offered to a selector: a UTxO at a script payment credential, one carrying a datum or a reference script, and one at a franken-flagged payment credential. Anyone can create an output that pairs their own payment key with another wallet's stake credential (CIP-0019, "Delegation part"), so such a credential may not be the wallet's; the study calls these franken addresses. In a wallet with two or more key payment credentials, a credential is flagged if it never appears as an input in a transaction that also spends another of the wallet's key payment credentials. The rule reads the wallet's whole history up to the snapshot, and flags nothing in a wallet where no pair of credentials co-spends.

A spend event is a transaction that consumes a wallet output at a key payment credential. Its intent:

- **Requested outputs.** Every output to another stake credential, and every wallet output at a script payment credential or carrying a datum or a reference script, as observed. From the wallet's other outputs, the net inflow of each native asset that did not come from a wallet input (it came from a non-wallet input or a mint) becomes requested wallet outputs at their minimum, each at the address of the observed output that received it. Every other wallet output is change. A requested output whose coin is below the minimum at the snapshot (coins per UTxO byte at the snapshot times 160 plus the output's size as written, the ledger's rule and the kit's) is raised to it, the raise recorded with the minimum-UTxO rule of its transaction's era: Mary (protocol major 4 and below), Alonzo (5 and 6), or Babbage and Conway (7 on).
- **Implicit values.** Withdrawals, refunds, deposits, the treasury donation, mints and burns, read from the transaction's fields and checked against db-sync's `withdrawal`, `tx.deposit`, `ma_tx_mint` and `tx.treasury_donation`. Deposits follow each certificate's rule in the Conway CDDL (`conway.cddl:30-48`, `:429-540`): a Shelley-era registration or deregistration at the epoch's key deposit, Conway's registration and deregistration certificates and DRep certificates with their stated coin, and proposals with theirs. A pool registration pays the pool deposit only when the pool is new, which the bytes do not say; its deposit is the remainder of db-sync's net deposit, which must be a whole number of pool deposits.
- **Fixed parts**, each as its original bytes:
  - non-wallet inputs and held wallet inputs, with their resolved outputs, and reference inputs;
  - every body field except the inputs, outputs and fee, the two hashes a builder recomputes (7 and 11), and collateral (13, 16 and 17);
  - the witness-set entries other than the wallet's own payment-key witnesses;
  - the redeemers, each with the item it points at, resolved in the ledger's order: inputs by transaction id then index, policies by bytes, reward accounts by network then credential (a script credential before a key) then hash, voters by kind (committee, DRep, pool) then credential, certificates and proposals as listed;
  - the auxiliary data.

  The script fee is the execution term `ceiling(priceMem * mem + priceStep * steps)` (`libs/cardano-ledger-core/src/Cardano/Ledger/Plutus/ExUnits.hs:198-203`) plus the Conway reference-script term, both under the snapshot's parameters. The reference-script term's price per byte grows by 1.2 for every further 25,600 bytes (`eras/conway/impl/src/Cardano/Ledger/Conway/Tx.hs:105-145`), over the reference scripts of the inputs and reference inputs (`eras/conway/impl/src/Cardano/Ledger/Conway/UTxO.hs:149-171`). The bytes of the fixed parts are the observed size less the size of the same transaction with them removed.
- **Collateral** is required when the transaction carries a redeemer or is phase-2-invalid; the observed collateral is kept for reporting. A phase-2-invalid transaction is an intent whose only effect is the loss of its total collateral.
- **Spend type**, in this order: T6 script execution (a Plutus redeemer, or phase-2-invalid; native scripts never count), T8 mint or burn, T7 certificate or governance, T5 fungible tokens sent, T4 NFTs of several policies, T3 several NFTs of one policy, T2 one NFT, T1 pure-ADA payment. An asset's class: a valid CIP-67 label decides (333 and 444 fungible; 222, 100 and 500 non-fungible unless more than one unit is held), otherwise more than one unit makes it fungible (CIP-0067, "Specification"; CIP-0068, "Labels", "333 FT Standard", "444 RFT Standard"). The units are the largest of the wallet's holding at the window's start, at its end, and the units the transaction moved.

Every intent is checked before it is written. db-sync's consumed inputs (the body inputs, or the collateral inputs of a phase-2-invalid transaction) and its outputs must be the transaction's. Coin and every asset must be conserved with the implicit values. The transaction rebuilt from the intent's parts and the observed wallet inputs, change and witnesses, each part's original bytes, must have the transaction's exact body hash and size. Before a history file is complete, its observed events replayed from the start state must reach the wallet's UTxO set at the window's end. Any failure stops the run with the transaction named.

A burst is a maximal run of the wallet's spends with no more than 60 seconds between consecutive block times. It is chained if any of its transactions spends an output of an earlier transaction of the same burst, transactions in one block ordered by their index; parallel otherwise.

For every asset held at a window's start, the arrival table names the transaction in which it first entered one of the wallet's outputs over the whole history, or the creating transaction of the UTxO holding it, flagged, when none is found.

The census measures value bytes as the ledger's serialization of the Value (`eras/alonzo/impl/src/Cardano/Ledger/Alonzo/Rules/Utxo.hs:425-447`) and a UTxO's minimum with CSL on the output re-encoded from db-sync's columns. The value-size limit in force is `max_val_size` from Alonzo on, and the Mary era's 4,000-byte constant before it (`eras/allegra/impl/src/Cardano/Ledger/Allegra/Rules/Utxo.hs:249-264`).

## The simulator core

### The ledger kit

Every size is the ledger's size of the transaction's bytes, never an estimate, and every fee is `minFeeA * size + minFeeB`, plus for a replayed script spend the intent's script fee (`eras/alonzo/impl/src/Cardano/Ledger/Alonzo/Tx.hs:498-508`; `eras/conway/impl/src/Cardano/Ledger/Conway/Tx.hs:105-145`). The wallet-controlled fee, which every fee comparison uses, is that fee less the script fee and less `minFeeA` times the bytes of the intent's fixed parts.

Every built transaction is checked from its bytes, without CSL, so that the checks are a second implementation beside the treatment's and the libraries' own: the size limit (`eras/shelley/impl/src/Cardano/Ledger/Shelley/Rules/Utxo.hs:570-585`); every output's Value, the collateral return's included, at most `maxValSize` (`eras/alonzo/impl/src/Cardano/Ledger/Alonzo/Rules/Utxo.hs:425-447`); every output's coin at least `coinsPerUtxoByte * (160 + its bytes)` (`eras/babbage/impl/src/Cardano/Ledger/Babbage/TxOut.hs:678-702`); every input resolving; coin and every asset conserved with the withdrawals, refunds, mints, deposits, burns and treasury donation (`Shelley/Rules/Utxo.hs:513-529`; `eras/conway/impl/src/Cardano/Ledger/Conway/UTxO.hs:107-145`); the fee at least the minimum (`eras/babbage/impl/src/Cardano/Ledger/Babbage/Rules/Utxo.hs:183-212`); one vkey witness per distinct key among the key payment credentials of the inputs and collateral inputs and the keys of the transaction's required signers, together with the keys of the intent's fixed witnesses that its fixed inputs and required signers do not account for, each distinct key once, so a stake key that a library also writes as a required signer needs one witness (`eras/alonzo/impl/src/Cardano/Ledger/Alonzo/TxBody.hs:307-313`; `eras/shelley/impl/src/Cardano/Ledger/Shelley/UTxO.hs:205-227`; `eras/conway/impl/src/Cardano/Ledger/Conway/UTxO.hs:172-180`); the auxiliary-data hash present exactly with auxiliary data; and, with redeemers, collateral: one to `maxCollateralInputs` inputs at key addresses, the balance less the return ADA only, at least `collateralPercent` of the fee, and equal to the total-collateral field (`Babbage/Rules/Utxo.hs:231-308`; `eras/babbage/impl/src/Cardano/Ledger/Babbage/Collateral.hs:30-39`). A failed check is a build failure of one class: transaction size, value size, change minimum, maximum input count, balance, fee under the minimum, collateral or other. A fee under the minimum (`fee-minimum`) is reported apart from balance shortfalls: the transaction balances, and the network rejects it for its fee alone.

A selection-only method's transaction is assembled with CSL: its inputs sorted by transaction id then index, its outputs, and synthetic vkey witnesses, one per distinct payment key, of the size real ones have, at the minimum fee found as a fixed point (the fee's and the change coin's encodings are part of the size). A replayed intent's transaction is assembled from its parts: the requested outputs and every fixed part as their original bytes, the arm's inputs and change, spend redeemers re-indexed to their inputs' places, the auxiliary-data hash recomputed, collateral under the arm's rule with its return output and total, and synthetic vkey witnesses beside the intent's fixed ones. There is one synthetic witness per distinct key among the payment keys of the arm's inputs, the wallet's held fixed inputs and the collateral input, plus the keys of required signers that have no fixed witness. The history reader keeps only the witnesses of keys other than those of the wallet inputs the observed transaction spent. So a required signer without a fixed witness is a wallet key, and the ledger needs its witness whichever inputs the arm chooses. The script-data hash is a 32-byte stand-in over the redeemers and datums: the ledger's also covers the cost models' language views, which a history file does not carry, and no check reads it. Four negative controls are caught on every form of transaction, each by its own check: the fee one lovelace short, the size one byte over, a Value one byte over, and one witness short.

### States, the treatment and the methods

A state holds the wallet's UTxO records (in `txid#index` order), its stake credential, its franken-flagged credentials and its change address. The change address is the address of the latest output at a key payment credential and a base address, by creating transaction then index and passing over franken-flagged credentials, among every output the wallet has received on the chain up to that point: `latestKeyBase`, then the deposits and the observed wallet outputs of the window's spends and self-reorganizations, the real wallet's own change included. Every arm and method therefore has the same change address at a given spend, and it moves as later outputs arrive; an event's own outputs count from the next event on. A wallet that spends, or holds a spendable UTxO, before it has received such an output, or never receives one, is refused. Applying a transaction removes its wallet inputs and adds its outputs that carry the wallet's stake credential; payments to other stake credentials leave the wallet.

The treatment is loaded from the directory the operator names, every file's digest checked against `data/treatment-pins.txt` first. Its planner and its H-12 selection rule run on states, given the UTxOs in `txid#index` order with held UTxOs marked held, and every transaction they build must pass both the treatment's own checks and the kit's; a disagreement stops the run. Protocol parameters reach it as its parameters object, and a parameter it would read differently from the run's is refused.

A method is `{ name, version, deterministic, seeded, build(state, intent, params, opts) }`. `deterministic` says that it draws nothing at random, and `seeded` that its answer is fixed by its inputs and the seed it is given: true for every deterministic method and for `cjs-rrri`, `mesh-rrri` and `lace-rrri`, which draw from that seed, and false for `csl-ri` and `cml-ri`, whose libraries draw from a generator no caller can seed, so that their runs cannot be repeated. The contract refuses a deterministic method that is not seeded. `opts` names a seed, a change policy, the arm's collateral rule, H-12's absorption, for a replayed script spend the collateral the engine has set aside, and in a replay the job's random source (`opts.random`). A method whose library chooses its own collateral declares `ownCollateral` and is given none; only the Evolution SDK's `evo-lf`, the survey's `evo-unfrack` and Lucid Evolution's `lucid-lf` may (`choosesOwnCollateral` in `src/methods/contract.mjs`). Methods are made by name (`src/methods/registry.mjs`), so that a worker thread can make the one its job names: the sixteen baselines `csl-lf`, `csl-ri`, `cjs-rrri`, `evo-lf`, `blaze-wd`, `lucid-lf`, `mesh-rrri`, `typhon-lp`, `helios-sf`, `cml-lf`, `cml-ri`, `cometa-lf`, `lace-rrri`, `adalite-lp`, `yoroi-lf` and `apollo-macs`, each made from the loaded treatment at its library's defaults with no options at creation (a build still takes `opts`), the H-12 method and the two test methods. The builder survey's other subjects (`evo-unfrack`, and Mesh's `mesh-default` and `mesh-lf`, which run Mesh's own callbacks) are not registered, so no run plan can name them. The adapters load with the registry, so every worker loads them: a worker's V8 heap after loading the treatment and the registry is about 49 MB, against 12 MB with the treatment alone. The H-12 method serves the replays. For a replayed intent its request carries every part the intent holds: fixed inputs, reference inputs, body fields, witnesses, redeemers, auxiliary data, script fee, implicit values, requested outputs as their own bytes, and the collateral set aside. The rule takes each into its selection, size and fee (`methods/h12.mjs`). The two test methods exist only to test the engine and never appear in a study run: `test-largest-first` (largest coin first, with a simulator-owned change policy) and `test-stall`, which blocks its thread to force the watchdogs. The simulator's change policy, put on a baseline's input selection, is built from the treatment's own functions: `layout`, the layout-preserving change.

### Arms and run plans

The one arm is `observed`: the wallet as it was at the window start, untidied (`src/arms/arms.mjs`). The planner's plan fees are recorded as 0. A variant tells UnFrack.It's two H-12 runs apart, `absorb-on` and `absorb-off`; every other job's variant is `default`.

A run plan lists which jobs run in which window under which selectors and change policies (`src/arms/plan.mjs`, `windowPlan`). The study's plan is the same in both windows and replays the observed state only, to answer two questions. For each library role, `csl-lf`, `csl-ri`, `cjs-rrri`, `evo-lf`, `blaze-wd`, `lucid-lf`, `mesh-rrri`, `typhon-lp`, `helios-sf`, `cml-lf`, `cml-ri`, `cometa-lf`, `lace-rrri`, `adalite-lp`, `yoroi-lf` and `apollo-macs`: the library's inputs with its own change (`L/own`, change policy `default`, labeled Q1) and with UnFrack.It's change (`L/layout`, change policy `layout`, labeled Q1 and Q2). Question 1 compares `L/layout` with `L/own` per library; question 2 compares UnFrack.It's H-12 rule with `L/layout`. For the rule, `unfrackit-h12` with its own change, once with absorption on (variant `absorb-on`) and once with it off (`absorb-off`), labeled Q2. The job's `opts.absorb` reaches the method, and the `wallet-arm` record's `absorb` field shows it. The variants tell the two jobs apart in a record's key. A library that picks at random (`csl-ri`, `cjs-rrri`, `mesh-rrri`, `cml-ri`, `lace-rrri`) runs 10 repetitions (`--reps` overrides, for tests); a deterministic one and the rule run once. Repetition r seeds the selector with r in `L/own` and `L/layout` alike (`replayJobOpts` in `src/replay/run.mjs`), so the two share one seed sequence. `csl-ri` and `cml-ri` draw from their libraries' own generators, which a caller cannot seed, so their draws differ between the two jobs whatever the seed. At sixteen libraries that is 2 + 20 + 20 + 2 + 2 + 2 + 20 + 2 + 2 + 2 + 20 + 2 + 20 + 2 + 2 + 2 + 2 = 124 jobs per wallet and window. Each study library is one row of `LIBRARY_TABLE` in `src/arms/plan.mjs`: its role, its method, and whether it picks at random. The study's roles, the test roles and each role's repetitions come from that table. Every job runs under one collateral rule ("The study run" above) when its window holds a script interaction, and is recorded with the collateral field `none-needed` otherwise. The Evolution SDK and Lucid Evolution build `L/layout` like the other libraries (`layoutOnLibraryInputs` in `methods/evo.mjs` and `methods/lucid.mjs`). Each makes the library call it makes for `L/own` and reads the wallet inputs it selected and the collateral it chose from the transaction. Each then drops the library's change outputs and builds UnFrack.It's change on those inputs through `methods/change.mjs`. The collateral stays as the library wrote it (its inputs, its total collateral and its return output), since the library cannot be given the UTxO the engine sets aside. The other libraries' `L/layout` jobs assemble the engine's set-aside UTxO. Inputs that cannot fund the layout change fail with class `change-minimum`; a library failure is the library's. When the H-12 rule answers a script spend with a chain, the planner's transactions carry no collateral and the payment carries the collateral set aside. The tests run this plan with the test method in every role (`TEST_ROLES`). A replay job, one (wallet, window, arm, variant, selector, change policy, collateral rule, seed), makes one mulberry32 generator from its seed when it starts. Every build of the job draws from it in the order the engine makes them, the burst pass included (`jobOptions` in `src/replay/engine.mjs`). Jobs compared with each other therefore start from the same stream whichever worker runs them. A caller cannot give a replay a generator of its own.

### The replay engine

Each (wallet, arm, variant, selector, change policy, collateral rule, repetition) replay runs in a worker process to completion, under the watchdog of "Workers and watchdogs" above. Workers are replaced after 40 jobs, or sooner when they have grown, since CSL's WebAssembly memory only grows to the largest wallet a worker has built for; the pool starts jobs within a memory budget ("Worker memory" above). A job on the 3,005-UTxO shape M2 peaks at 0.3 to 0.6 GiB. Between spends the engine settles the heap (`src/kit/heap.mjs`). It forces two full collections, each followed by a turn of the event loop so that CSL's finalizers run. It does this only once the process's external and ArrayBuffer memory has grown by 48 MiB since the last settle. A worker also keeps the BLAKE2b digests of inputs up to 4 KB (`src/history/blake2b.mjs`), so that later jobs hash less. This changes no record. Deposits enter every arm when they occurred; held UTxOs leave every arm that holds them when anything consumes them; self-reorganizations are counted and their reshuffles not replayed, but one that carries a reward withdrawal deposits the withdrawn ADA in every arm, as one UTxO at the change address in effect at it, so that every arm receives what the real wallet received, its fee charged to no arm. Every arm replays the same intents in the same order, each without two parts that the observed transaction's builder added and the spend does not need: the network id (body field 15), and an auxiliary data holding no metadata and no script, in any of its three encodings, with its hash (body field 7). The ledger requires neither. They are left out before any method, feasibility test or check sees the intent (`withoutLeftovers` in `src/kit/replay.mjs`), and the intent's count of fixed bytes drops by their size. A library that writes either part itself keeps it and pays for it in its fee. The history file keeps both, and the reader's rebuild check rebuilds the observed transaction with them. In each arm:

- A phase-2-invalid intent forfeits the observed total collateral from collateral chosen under the arm's rule, its return output coming back to the wallet. With no eligible UTxO it is infeasible for collateral.
- An intent the arm's balance cannot fund, by the H-12 rule's exact test with the intent's implicit values and fixed inputs counted, is recorded as infeasible by balance and is not a selector failure.
- A script spend sets its collateral aside before any method selects (`setAside` in `src/replay/engine.mjs`), as a wallet with a dedicated collateral UTxO does: the UTxO the arm's rule chooses leaves the pool the method selects from, and every transaction the method assembles carries it as collateral. A script spend with no UTxO to set aside (reason `none-eligible`), or whose payment the balance cannot make without it by the same exact test (reason `payment`), is recorded as infeasible for collateral, apart from build failures and from infeasibility by balance, and is not a selector failure. `evo-lf`, `evo-unfrack` and `lucid-lf` have nothing set aside, since their libraries choose their own collateral and cannot be given one: they select from the whole pool, and the spend record marks the collateral as library-chosen. Their spend is infeasible for collateral (`none-eligible`) when the rule would set no UTxO aside, as for every method, since no method could build it; reason `payment` does not apply to them.
- Otherwise the method builds it from that pool, the kit checks it against the whole state, and it is applied; a failure leaves the state as it was and the replay continues. A failure of class `collateral` is a transaction whose collateral fails the kit's check, or a collateral the Evolution SDK or Lucid Evolution cannot make, charged to the method whether the engine or its library chose the collateral. A transaction whose collateral is not the UTxO set aside is a defect of the method, class `other`, except under the methods that choose their own. When the kit fails a transaction that carries parts its adapter wrote after the library priced it, the failure's detail ends with their names (`parts the library did not price: ...`). Every method's transaction also has its redeemers compared with the intent's, by tag and by the input, policy, reward account, certificate (its kind and credential), voter or proposal each redeems (`missingRedeemers` in `src/kit/replay.mjs`). The transaction's redeemer pointers are resolved as the history reader resolves the observed transaction's. A transaction that lacks one of the intent's redeemers fails, since the ledger rejects it (`MissingRedeemers`, `eras/alonzo/impl/src/Cardano/Ledger/Alonzo/Rules/Utxow.hs:251-274`, which Conway's UTXOW runs through Babbage's). The names in its detail include `redeemers`, whatever the failure's class. When the kit's checks otherwise pass, the failure is class `other`.
- A held output that a built spend's transactions create enters the state under the reference of the observed output its requested output stands for: the observed transaction's hash and the requested output's index, or, for a requested output made from an inflow, the index of the observed output it came from (`heldOutputRefs` in `src/state/state.mjs`). Such an output is an order or a lock at a script address that carries the wallet's stake credential, or an output with a datum or a reference script. The events and later intents that consume it name that reference: a held-consumed event, a held fixed input, and the held UTxOs a self-reorganization or a phase-2-invalid intent consumed. Where the spend was not built, the UTxO never enters the arm. A held output is matched to a requested output by its bytes, or else by its address, coin, assets, datum and reference script, for a library that writes an output in another encoding, as CSL does when it puts a policy's asset names shortest first. One that matches no requested output keeps the built transaction's reference and is counted in `heldUnmatched`; since change never goes to a held address, only a method that alters a requested output makes one. A later intent that spends such a UTxO as a fixed input is built and checked against the UTxO the arm holds (`heldInputsFromState`), which differs from the observed one when the history reader raised the requested output's coin to its minimum.

Collateral is the smallest UTxO eligible under the arm's rule, ties by `txid#index`, that is not one of the spend's fixed inputs and can carry, with a return output at its minimum, the total collateral of the largest fee the spend can have: a transaction of `maxTxSize` bytes with the intent's script fee. It covers any fee a transaction within the size limit reaches. The ledger allows a collateral input that is also a spent input: Conway's UTXO rule runs Babbage's, which checks the collateral UTxOs alone (`feesOK` and `validateTotalCollateral`, `eras/babbage/impl/src/Cardano/Ledger/Babbage/Rules/Utxo.hs:195-212` and `:241-256`), requires only that every spent, collateral and reference input be in the UTxO (`:388-390`), and keeps only the spent and reference inputs disjoint (`disjointRefInputs`, `:215-229`). The kit accepts such a collateral; only the Evolution SDK's and Lucid Evolution's collateral can be one, since the UTxO set aside is out of every other method's pool. A forfeit's collateral is the smallest eligible UTxO that can carry the forfeit. At every script interaction the engine records whether collateral is available under each rule. At a spend, that is whether the rule would set a UTxO aside and leave enough to make the payment, so a spend that would be infeasible for collateral counts as having none (a spend infeasible by balance needs only the UTxO). At a forfeit, it is whether any UTxO is eligible. At each parallel burst's first spend, a separate pass builds the burst's spends from the state at its start without spending any output created earlier in the burst, for burst feasibility; the sequential replay continues for fees.

The window-end `conformity` of a `wallet-arm` record is computed on the end state before any restoring plan. `tokenUtxos` counts the UTxOs that are not held and carry a native asset. `conforming` counts those that break none of the treatment's output rules at the planner's decided defaults and the run's parameters: no fungible and non-fungible tokens together, isolation respected when on, at most `bundleSize` tokens, Value bytes at most `maxValSize`, coin equal to its minimum, no zero quantity. `conformingNoCoin` is the same count with the coin rule left out, by giving each UTxO's own coin as its minimum. Nothing is exempt: a partial split's remainder, or an output that absorbed dust change, counts as non-conforming when it breaks a rule. The verdict is the treatment's `outputViolations`, called with each UTxO's tokens, coin, minimum coin and Value bytes read from the state without CSL (`src/replay/conform.mjs`), and the class map is the treatment's `classifyAssets` over every UTxO of the state, held ones included, so the count does not depend on the planner accepting the state. A wallet with no token UTxO has no share. Beside the counts, `proposes`, `txs` and `fee` are the plan the planner would propose for the end state (the restoring plan; `fee` is its fee), `refused` carries the planner's refusal when it refuses the state (the counts are still present), and `noChangeAddress` marks a state with no change address.


### Synthetic shapes and streams

The 17 shapes of the preprod seeder, S1 to S9, S2b, M1 to M5, M7 and M8 as its specification names them (byte for byte the treatment harness's), and the claim and merchant shapes CL1, CL3, E1 and E2 are generated deterministically with mulberry32. Each shape has a synthetic intent stream of fixed test values for the engine's tests, over 75 days: payments of each type T1 to T8 that its holdings allow, a deposit with a held datum UTxO, a parallel burst, a deposit at a second base address of the wallet, to which the change address moves, a Plutus spend with a script input, redeemer, script and datum, a phase-2-invalid forfeit, a payment with a validity interval, a message and a held fixed input, a self-reorganization, one with a reward withdrawal, a native-script mint, a stake registration with its deposit, and two 30-day marks.

### Heavy synthetic wallets

The 21 shapes top out at 3,005 UTxOs and a 75-day stream of about 13 intents, so they cannot show what a wallet near the 20,000-UTxO ceiling costs in memory and time. `src/shapes/heavy.mjs` generates one from its name, `H<k>E<e>`: exactly k thousand UTxOs and exactly e thousand events, where a leading zero in e reads as a fraction (`H20E05` is 20,000 UTxOs and 500 events, `H3E6` 3,000 and 6,000, `H20E01` 20,000 and 100, `H20E1` 20,000 and 1,000). k runs from 1 to 30 and the events from 10 up. A name gives the same wallet and stream on every run, from mulberry32 seeded from the name and BLAKE2b hashes of the name and a counter.

The wallet has one UTxO in a hundred as pure ADA (20 to 100 ADA, at least 5), and splits the rest 85% non-fungible and 15% fungible. A non-fungible UTxO holds one token in a policy of 100 names; a fungible UTxO holds one piece of 500 to 1,500 units, an asset has 50 pieces, and a policy has 5 assets. All sit at the change address of the treatment's payment key 0, in shuffled order.

The stream runs over max(30, the event count divided by 12, rounded up) days with its events evenly spaced. It draws T1 payments of 2 to 20 ADA for half the intents and T2 to T5 token sends for the rest, from the tokens the stream has not yet sent, and falls back to a T1 when the holdings cannot express a draw. A 150 ADA deposit follows every 8 intents; every fourth deposit adds a token of a new policy and every fifth a piece of a fungible asset. Every 50th intent is a parallel burst of two payments, every 100th from the 25th a Plutus spend with collateral, and a mark falls every 30 days. Outputs are serialized as in the fixed streams. `loadSource` and `shapeState` take the names like any shape's, and so does `replay --shapes`, beside the fixed shapes; `--shapes all` remains the 21 fixed shapes. A record names a shape in at most six characters, so that command refuses a longer heavy name, such as `H20E005`, before anything runs.

### The fidelity check

For every observed spend that runs no script, the `fidelity` command rebuilds the transaction with the ledger kit from the spend's parts in its history file and compares two minimum fees: `minFeeA * |rebuilt| + minFeeB` and `minFeeA * |observed| + minFeeB`, both under the fee parameters of the observed transaction's epoch, which db-sync's `epoch_param` gives and every intent carries. A spend is within the tolerance when the two differ by at most 2% of the observed one (`|rebuilt - observed| * 50 <= observed`). A window passes when at least 99% of its spends are within it. The sizes need not be equal, since the kit writes its own encodings: sets with tag 258, change in the array form and synthetic vkey witnesses.

The rebuild is the replay's assembly (`assembleReplayOnce` in `src/kit/replay.mjs`) at the minimum fee found as a fixed point, as every replayed transaction is, from:

- the intent as a replay gives it to every method, without the network id and without auxiliary data holding no metadata and no script;
- the observed wallet inputs and the intent's fixed inputs;
- the requested outputs that are outputs of the observed transaction, and every other observed wallet output as change. A requested output built from an inflow is left out, since the wallet output that received the inflow already carries it;
- one synthetic vkey witness per distinct key among the payment keys of the wallet inputs and held wallet inputs and the keys of required signers with no fixed witness, as in every replay. Every other witness is kept as observed, a bootstrap witness of a non-wallet Byron input at its own size;
- no collateral.

The wallet's UTxO set is followed through the history file's events and must end at the file's end count (`stateCheck`).

A spend runs a script when it carries a Plutus redeemer or is phase-2-invalid (spend type T6), and the check leaves it out. Native scripts and reference scripts stay in: neither adds an execution term, and both fees use the same formula. Self-reorganizations are counted beside the check, since the replay does not rebuild them and a history file does not carry their fixed parts. A spend the kit cannot assemble, such as one carrying a body field 6, is counted apart with its reason and counts against its window's share; the share over the rebuilt spends is recorded beside it.

`fidelity.json` holds, per window (the history files' frame):

- the files, wallets and splits; the intents, the script spends left out and the self-reorganizations;
- the spends checked, rebuilt, within 2% and outside it, and those counted apart by reason;
- the share, the share over the rebuilt spends, and whether the share reaches 99%;
- the quantiles of the relative difference at 0, 1, 5, 25, 50, 75, 95, 99 and 100% (nearest rank), its mean and its signs, and the same quantiles of the byte difference;
- the within count and relative quantiles with the leftovers kept, which separates the replay's rule on leftovers from the kit's encodings;
- over every rebuilt spend, over those outside 2% and over those more than 1% away, counts by spend type, protocol major version, kit witnesses less observed wallet witnesses, bootstrap witnesses, native scripts, other vkey witnesses, network id left out, empty auxiliary data left out, change in the map form, and collateral fields on the observed transaction.

It holds no fee, size or identifier of a spend. For the study, the check runs once over the exploration split's history files of both windows after the draw:

```
node src/cli.mjs fidelity --treatment <dir> --history <run directory>/history --run-id <id>
```

A confirmation-split file is refused unless `--analysis-freeze-tx` names the transaction whose record freezes the analysis scripts.

Replay path. A replayed intent can carry parts a plain payment intent (requested outputs only) never does: fixed parts (inputs the selector does not choose, reference inputs, certificates, withdrawals, the mint field, validity, required signers, votes, proposals, the treasury fields, auxiliary data and witnesses), collateral for a script spend, implicit values (withdrawals, refunds, deposits, a donation, a mint or a burn), and requested outputs that carry a datum or a reference script. Each adapter states which of these parts its replay path covers (`REPLAY_COVERAGE` in `src/methods/library.mjs`), and before it builds anything it refuses an intent with a part it does not cover (`refuseUncovered`). `cjs-rrri`, the CSL methods, `evo-lf`, `blaze-wd`, `lucid-lf`, `mesh-rrri`, `typhon-lp`, `helios-sf`, the CML methods, `cometa-lf`, `lace-rrri`, `adalite-lp`, `yoroi-lf` and `apollo-macs` cover every part; the collateral of `evo-lf` and `lucid-lf` is their libraries' own choice, since neither library can be given the UTxO the engine would set aside (below). The survey's Mesh subjects cover none, since the survey runs payment intents only. A refusal is an ordinary error, so the engine records it as a failed spend of class `other` with its message, never as not replayable (`src/replay/engine.mjs`).

`cjs-rrri` passes each part through the library's own parameters for what a selection has to balance, and through the ledger kit for the rest:

| Part | How `cjs-rrri` replays it |
|---|---|
| Fixed inputs: other parties' and script inputs, and the wallet's held UTxOs the spend consumes | `preSelectedUtxo`. The selection starts from them, their value counts toward every target, and their tokens that no output requests go to the change. They are never offered as ordinary UTxOs. |
| Withdrawals, refunds, deposits | `implicitValue.coin`: `withdrawals`, refunds as `reclaimDeposit`, withdrawals and refunds summed as `input`, and deposits as `deposit` |
| A treasury donation | added to `implicitValue.coin.deposit`, which the library counts as coin spent outside the outputs. The library has no donation field. |
| A mint or a burn | `implicitValue.mint`, a burn as a negative quantity |
| Requested outputs | `outputs`, by address and value. The kit writes each as its own bytes, so a datum, a reference script and a coin raised to its minimum pass through as observed. |
| Every other fixed part: reference inputs, certificates, the withdrawal and mint fields, validity, required signers, votes, proposals, the treasury fields, auxiliary data, scripts, datums and redeemers | The library has no parameter for these; the values of the withdrawal and mint fields reach it through `implicitValue`. The kit writes each as its original bytes into every transaction the callbacks assemble and into the final one, so `computeMinimumCost` and `computeSelectionLimit` count their bytes. `computeMinimumCost` adds the intent's script fee, computed from the observed execution units. |
| Collateral | The UTxO the engine set aside under the arm's rule before selection (`setAside` in `src/replay/engine.mjs`), which is not among the UTxOs the library is given. Every transaction the callbacks assemble, and the final one, carries it with a return output and the total-collateral field. A script spend with no UTxO to set aside, or that cannot be paid without it, is infeasible for collateral and never reaches the library. |

An intent the kit cannot write, one with body field 6 (protocol parameter updates, which no Conway transaction carries), is not replayable for `cjs-rrri` and is counted apart from build failures. Every replayed intent's transaction is assembled by `src/kit/replay.mjs`, even one with none of these parts, so its requested outputs keep their bytes. A plain payment intent's transaction is assembled by `src/kit/assemble.mjs`.

`mesh-rrri` builds through `MeshTxBuilder` as a dapp calls it for a payment: `txOut` for each requested output, `changeAddress`, `selectUtxosFrom` with the wallet's spendable UTxOs in the state's order, and `complete()`. Before `complete()`, the adapter wraps the builder's own default selector, `CardanoSdkInputSelector`. The wrapper calls it with the builder's preselected inputs, outputs, candidates and change address as given, and replaces two things: the four constraint callbacks, with the exact ones in Mesh's form, and the implicit value, with the intent's. Mesh's own callbacks price a clone of the builder as Mesh serializes it, take the minimum coin at the library's stub address, and size a token bundle with no coin. Mesh's selector sums the requested outputs into one output at a placeholder address before it selects. On a spend with several requested outputs, the library therefore writes its change for that one summed output, where `cjs-rrri` writes a change bundle per output. Mesh also writes an empty auxiliary data (the tag-259 empty map) and its hash into every transaction that carries no metadata, 38 bytes that `cjs-rrri`'s transactions do not carry, and the callbacks price them. The kit assembles the transaction, as for `cjs-rrri`, from the inputs, change and fee Mesh wrote, with Mesh's auxiliary data where the intent has none of its own. On the payments of S1, S6, M1 and CL1, the body the kit writes is byte for byte the body Mesh serializes. The parts reach Mesh's selection as follows:

| Part | How `mesh-rrri` replays it |
|---|---|
| Fixed inputs: other parties' and script inputs, and the wallet's held UTxOs the spend consumes | `txIn` with each input's value, address and reference-script size, so the builder hands them to its selector as preselected inputs. They are never offered as candidates. |
| Withdrawals, refunds, deposits, a treasury donation | Mesh's `ImplicitValue`: `withdrawals`, refunds as `reclaimDeposit`, and deposits as `deposit`, with a donation added to `deposit` as for `cjs-rrri`. The builder's own implicit value is zero, since it is given no certificate, withdrawal, mint or proposal. |
| A mint or a burn | `ImplicitValue.mint`, a burn as a negative quantity |
| Requested outputs | `txOut` with the output's address and value, which is all the selector reads of them. The kit writes each as its own bytes. |
| Every other fixed part, and the collateral | As for `cjs-rrri`: the kit writes them into every transaction the callbacks price and into the final one. |

An intent with a part that CSL has no way to express is not replayable for the CSL methods and is counted apart from build failures. Such parts are body field 6; a deposit or refund that CSL counts differently from the transaction (CSL charges a pool deposit for every pool registration); a script, datum or redeemer that a part needs and the intent does not hold; and a part that CSL refuses, or a script that CSL reads under another hash. An intent whose witness set holds a script or a redeemer that no part CSL builds takes is not replayable either. Under a substituted change policy, the simulator's policy receives only the inputs `add_inputs_from` chose, not the fixed inputs, and the kit assembles the transaction with the fixed parts and the collateral.

`evo-lf` passes each part through the Evolution SDK's own operations where it has one, and its execution units through the build's evaluator:

| Part | How `evo-lf` replays it |
|---|---|
| Fixed inputs: other parties' and script inputs, and the wallet's held UTxOs the spend consumes | `collectFrom`, one input per call with that input's redeemer. An input that holds a datum hash at a Plutus script address also gets its datum from the witness set, through `collectFrom`'s `datums`, with the bytes observed on chain, which its datum hash covers; the library writes that datum in the witness set and counts it in its fee. Fixed inputs are never among the UTxOs the library may select. |
| Reference inputs | `readFrom` |
| A mint or a burn | `mintAssets` per policy, a burn as a negative quantity, with the policy's redeemer |
| Certificates | The operation that writes the same certificate (`registerStakeLegacy`, `registerStake`, `delegateToPool`, `registerAndDelegateTo`, `registerPool`, `registerDRep` and the others), in the intent's order. The library takes a Conway certificate's deposit or refund from the run's parameters, and counts none for a legacy registration (kind 0) or deregistration (kind 1), so such a spend's change is off by the deposit and the kit fails it with class `balance`. |
| Withdrawals | `withdraw` per reward account, on the chain's network |
| Votes and proposals | `vote` per voter, and `propose` per proposal with the run's `govActionDeposit` as its deposit |
| Required signers, validity, metadata | `addSigner`; `setValidity`, each slot given as the chain's Unix time; `attachMetadata` per label, written as the library's Conway auxiliary data |
| Scripts and redeemers | `attachScript` for each native and Plutus script of the witness set, before the inputs are collected. Each redeemer goes with its operation, found by its target's key (`redeemerKey` in `src/kit/replay.mjs`; a voter's by its key hash, the only part of a voter the library's objects give), and `BuildOptions.evaluator` returns the observed execution units at the index the library gives it. The reference-script price is the run's, passed in `fullProtocolParameters`; without it the library charges 44 lovelace per byte. |
| Requested outputs | `payToAddress` with the output's address, value, datum and reference script, the coin as written, in the library's encoding |
| Refunds and deposits | The library computes them from the certificates and proposals above, except for a legacy registration or deregistration, for which it counts none. |
| Vkey witnesses | The library's fake witnesses for the wallet's keys that a replay witnesses (the payment keys of the inputs, held inputs and collateral, and the required signers with no fixed witness), and the intent's other vkey witnesses as observed. When the transaction then carries more vkey witnesses than the library priced, the observed ones are a part the library did not price, and a failure's detail names them: the library counts no DRep or committee key witness. |
| Collateral | The library's own choice from the UTxOs it is given, which are the whole pool: pure ADA first, then the largest, at most three, until they reach 5 ADA (its `setCollateral` default), and that fixed amount is the total collateral whatever the fee. It may be an input the library also spends. No operation or build option names a collateral UTxO, so the engine sets nothing aside for `evo-lf` and records the collateral as library-chosen. A collateral the kit's check refuses, or one the library cannot make (fewer than 5 ADA among three candidates, or a return under its minimum), fails with class `collateral`, charged to the library. |

A part the library's builder can neither write nor price goes on the transaction the library built, through the library's own types, so the replayed transaction carries every part of the replayed intent. These parts are the treasury fields (body fields 21 and 22), auxiliary data carrying scripts, which `attachMetadata` cannot write, a witness-set datum that no spent input needs, such as an output's, which `collectFrom` refuses (written with every observed datum and the script-data hash from the library's own function), bootstrap witnesses, and the certificates or withdrawals when one belongs to a script stake credential with no redeemer, which the library's stake operations refuse. The library's fee does not count such a part, and a donation or deposit it did not balance stays unbalanced, so the kit fails the spend with class `fee-minimum` or `balance` and the failure's detail names the part. No operation writes a network id or an auxiliary data without metadata or scripts either, and a replayed intent carries neither. Only a part the library's types cannot hold makes the intent not replayable for `evo-lf`: body field 6, as for `cjs-rrri`, a Byron address on a fixed or reference input, and a genesis-delegation or MIR certificate. The adapter, given a network id or an empty auxiliary data directly, finds them not replayable too. The transaction has the library's default encoding, since no `codecOptions` is given: the library writes redeemer data in its default Plutus data encoding, and writes a datum given through `collectFrom` with its observed bytes. The library computes a script-data hash only from full protocol parameters, over the cost models they hold. The simulator holds none, so the library hashes the redeemers with an empty language view, where the kit's replay assembly hashes the redeemers and datums alone. Both hashes are 32 bytes, and no check reads their value.

`blaze-wd` passes each part through a Blaze operation where one writes it: the requested outputs by `addOutput` with their own bytes, fixed inputs by `addInput` with their redeemers and datums, reference inputs, the mint, withdrawals, votes, proposals, required signers, validity, auxiliary data, the donation, and the scripts and datums of the witness set. The certificates go through the operation that writes the same certificate (kinds 1, 2, 3, 4, 7, 9, 16, 17 and 18). The execution units come from the provider's evaluator, which returns the intent's observed units, and the collateral is the UTxO set aside, given by `provideCollateral`. The library counts no DRep deposit or refund and counts a pool retirement as a refund, so such a spend fails with class `balance`. When a certificate has no operation (a legacy registration, a Conway deregistration, the combined kinds 10 to 13, the committee certificates), the whole certificate list goes on the library's transaction after it builds, unpriced, as do the current treasury value and bootstrap witnesses; the failure's detail names the part. Not replayable for `blaze-wd`: body field 6, a Byron fixed input, a network id, such certificates when one needs a redeemer, and a vote redeemer for a voter other than a script DRep.

`lucid-lf` passes each part through Lucid Evolution's own operations, and its execution units through `complete()`'s `evaluator` option, which it sets only for an intent with redeemers, since the run holds no cost models for the library's own evaluator:

| Part | How `lucid-lf` replays it |
|---|---|
| Fixed inputs | `collectFrom`, one input per call with that input's redeemer; an input holding a datum hash carries its witness-set datum |
| Reference inputs | `readFrom`. The library resolves a reference input's datum through its provider; for a hash the history does not hold, the offline provider answers a placeholder, which the library neither writes nor prices |
| A mint or a burn | `mintAssets` per policy, a burn as a negative quantity, with the policy's redeemer |
| Certificates | The operation that writes the same certificate (`registerStake` for the legacy registration, `register.Stake` with a redeemer for the Conway one, `deregister.Stake`, `delegate.ToPool`, `delegate.VoteToDRep`, `registerAndDelegate`, `register.DRep` and the others), in the intent's order, with each certificate's redeemer; the library takes each deposit and refund from the protocol parameters |
| Withdrawals | `withdraw` per reward account, with its redeemer |
| Votes and proposals | `vote` per voter and action; `propose` with the action as its observed CBOR and the observed deposit |
| Required signers, validity, metadata, treasury | `addSignerKey`; `validFrom` and `validTo`, each slot given as the chain's Unix time; `attachMetadata` per label; `donateToTreasury` with the donation and the current treasury value |
| Scripts and redeemers | `attach.Script` for each native and Plutus script of the witness set; reference scripts come with `readFrom`. The evaluator returns the observed units for each redeemer of the library's draft, matched by its target |
| Requested outputs | `pay.ToAddress`, or `pay.ToAddressWithData` with the output's datum and reference script; a datum hash whose datum the witness set holds is paid with that datum, so the library writes and prices it. The library raises a coin under its own minimum |
| Vkey witnesses | One synthetic witness per wallet key a replay witnesses, and the intent's other vkey witnesses as observed, through the library's `assemble` |
| Collateral | The library's own choice from the wallet's UTxOs, which are the whole pool: sorted as for selection and taken until they cover 5 ADA (its `setCollateral` default, or more when its fee estimate needs it) with a return output at its minimum, at most `maxCollateralInputs`. The wallet made by `selectWallet.fromAddress` offers no collateral of its own, so the engine sets nothing aside for `lucid-lf` and records the collateral as library-chosen |

Bootstrap witnesses, and auxiliary data whose metadata the library's metadata form cannot hold (a map key that is not text, an integer beyond 2^53, or scripts), go on the transaction the library built, unpriced, as for `evo-lf`. An intent is not replayable for `lucid-lf` when it carries body field 6 or a network id, a Byron address on a fixed or reference input, a legacy stake deregistration or a Conway registration without a redeemer (the library writes the other form), a certificate deposit or refund other than the run's parameter, a pool registration (the library writes the margin as a ratio of the margin to itself and fetches the pool metadata to hash it), a genesis-delegation or MIR certificate, a donation or a current treasury value without the other, a witness-set datum that no spent input or requested output takes, or a script the library reads to another hash (its script form holds a Plutus script wrapped twice in CBOR, so a script whose bytes are not already a CBOR byte string is wrapped once more).

`typhon-lp` writes the replay's parts through typhonjs's operations and types, since the library builds every part from its own types and takes no bytes. Requested outputs go in by `addOutput`, with their address, coin, tokens, datum and reference script read from their bytes. Fixed inputs go in by `addInput`, with their scripts, redeemers and datums. The rest are reference inputs with their reference scripts, the mint, certificates of kinds 0 to 2 and 7 to 18, withdrawals, votes, proposals, required signers, validity, the donation, the treasury value and the metadata. All of this happens before `prepareTransaction`, which takes the set-aside UTxO as its `collateralInputs`. A plain payment is `paymentTransaction` itself. An intent with fixed parts makes the same calls in the same order, with its parts added before `prepareTransaction`. The execution units are the intent's, on each redeemer. The library writes every output in the map form. A requested output whose coin is its minimum in the array form is therefore under its minimum as the library writes it, and the kit fails the spend with class `other`; `L/layout` writes the output's own bytes. A certificate of kind 3 to 6, a governance action with a parameter the library's type lacks, auxiliary data holding a script, and the witness-set datums, scripts and bootstrap witnesses no operation takes are put on the library's transaction after it builds, unpriced. These are not replayable for `typhon-lp`: body field 6, a network id, a Byron fixed input, a datum or native script whose bytes the library's encoding does not reproduce (it writes every non-empty list indefinite), a requested output address it re-encodes, a Plutus script whose bytes are not a CBOR byte string, a part written after the build that needs a redeemer, and a redeemer whose part it does not take.

`helios-sf` passes each part through Helios's own operations. The selector is asked for the requested outputs' value plus the deposits, the donation and the burn, less what the fixed inputs, the withdrawals, the refunds and the mint supply. For a payment with no fixed parts, that is the requested outputs' value.

| Part | How `helios-sf` replays it |
|---|---|
| Requested outputs | `addOutput` with each output decoded from its own bytes, so a datum and a reference script pass through; the library raises a coin under its minimum |
| Fixed inputs | `spendUnsafe`, with the input's redeemer where it has one; a datum-hash input carries its datum from the witness set, which the library writes |
| Reference inputs | `refer`, which also takes their reference scripts |
| Mint and burn | `mintPolicyTokensUnsafe` per policy, a burn as a negative quantity, with the policy's redeemer |
| Certificates | kinds 0 to 4, decoded by the library: `deregisterUnsafe` and `delegateUnsafe` with their redeemers, `addDCert` for the others. For a key credential the library also writes the stake key as a required signer |
| Withdrawals | `withdrawUnsafe` per reward account |
| Required signers, validity | `addSigners`; `validFromSlot` and `validToSlot` |
| Auxiliary data | the metadata, decoded by the library and written as a metadata map in its own encoding |
| Scripts | `attachNativeScript` and `attachUplcProgram` for the witness set's scripts |
| Collateral | the UTxO set aside, by `addCollateral`; the library then writes no collateral return |
| Execution units | `build` runs every Plutus script in the library's own machine, and again when it validates the transaction. The build option `modifyExBudget` gives each redeemer the intent's observed units. A script that fails in that machine, or costs more than those units there, fails the build with class `other` |

`build` validates the transaction before it returns it: the size of the unsigned transaction, the fee, the value conserved by its own count, the collateral, the scripts, and every output's minimum. Its balance counts stake-key deposits and refunds but no withdrawal, so a withdrawal of rewards leaves `L/own` unbalanced by exactly its amount, which the kit's check reports as class `balance`. An intent is not replayable for `helios-sf` when it carries body field 6, or any of body fields 19 to 22 (votes, proposals, the treasury value, the donation). The same holds for a certificate of kind 5 or above, a Byron fixed input, or bootstrap witnesses, which the library's types do not hold. It also holds for a native or Plutus V1 reference script on a reference input, a fixed or reference input the library cannot decode, a witness-set script it cannot decode, and a datum or script it reads to another hash. `@helios-lang/uplc` 0.7.20 reads no `case` term, so Plutus V3 scripts that use one fall here. Finally, it holds for auxiliary data holding scripts, and for a witness-set datum that no spent script input takes, since no operation writes one. A requested output the library refuses is a build failure of class `other`: `addOutput` refuses a script address with no datum unless its native script is in the transaction.

`cometa-lf` writes the replay's parts through Cometa's builder operations, before `build`. Requested outputs go in as the payment (`sendLovelace` or `sendValue`), or by `addOutput` when they carry a datum or a reference script. Fixed inputs go in by `addInput`, with their redeemers and datums. The rest are reference inputs, the mint per asset, withdrawals, votes, required signers, validity and the donation. Proposals go in with one operation per kind of governance action, and the library adds a guardrail script's redeemer itself. The metadata goes through `setMetadata`, given as the JSON the library reads. The witness-set scripts go through `addScript` and the remaining datums through `addDatum`. A certificate goes in through the builder's operation for it: stake delegation, Conway registration and deregistration, vote delegation to a DRep, DRep registration and update (each with an anchor), and DRep deregistration. The adapter does not use the generic `addCertificate`, because the 1.2.0 wrapper's `writeCertificate` releases the certificate it returns, which corrupts the module's memory. For the same reason the adapter never reads a script, an output or a UTxO back through the wrapper's readers, which free a signature script's key hash twice. It writes the library's types from the intent's bytes itself, and datums and redeemer data reach the library as their bytes, and the C library keeps those bytes unchanged. The set-aside UTxO is the collateral (`setCollateralUtxos`, with the change address for the collateral return). A spend that carries datums but no redeemer gets the change address and an empty collateral list, which `build` requires. The execution units come through the builder's evaluator, which gives each of the library's redeemers the intent's units for the part its index names. The builder takes the key, DRep and governance-action deposits only from its parameters, so a spend's own deposits (the ledger requires them to equal the parameters in force) are its parameters for that spend. The library writes every output in the map form and does not raise or check a requested output's coin, so a requested output at its array-form minimum fails the kit's minimum check with class `other`, as with `typhon-lp`. Its fee counts the reference scripts of reference inputs only. The adapter writes these parts on the library's transaction after the build, unpriced. They are a certificate list with one certificate no operation writes (such as a legacy registration, which then leaves its deposit unbalanced), a committee-update proposal or one with a parameter the library's type lacks, auxiliary data holding a script or a metadatum the library's JSON cannot carry, the treasury value, and bootstrap witnesses. These are not replayable for `cometa-lf`: body field 6, a network id, a script whose hash the library's encoding changes, a part written after the build that needs a redeemer, and a redeemer whose part it does not take.

`lace-rrri` passes each part through an operation of Lace's builder where one writes it, and writes the rest on the transaction `build()` returned, as `blaze-wd` does. The TTL of the default call, `expiresIn(7200)`, reads the clock; the adapter fixes the clock for that call at the spend's own slot, so the TTL is that slot plus 7200 whatever the time of the run. An intent's own validity interval replaces it. The seed is two draws of the job's generator, taken once per build, and the selector re-seeds from it on every balancing round.

| Part | How `lace-rrri` replays it |
|---|---|
| Requested outputs | `addOutput` with each output as `@cardano-sdk/core` reads its bytes, the operation `transferValue` ends in; the library re-encodes it |
| Fixed inputs | `addInput`, with the input's spend redeemer and, for a datum hash, its datum |
| Reference inputs | `addReferenceInput` |
| Mint and burn | `mintAssets` per policy with its redeemer, when every minted policy has one; a mint under a native script has no operation |
| Certificates | kinds 2, 7, 8, 9, 11 and 12 through the operation that writes each, kinds 2 and 7 with their redeemers; the library's balance counts their deposits and refunds |
| Withdrawals | `addRewardsWithdrawal`, or `addScriptWithdrawal` with the account's redeemer |
| Required signers, validity | `addRequiredSigner`; `setValidityInterval` |
| Auxiliary data | `setMetadata` per label, re-encoded by the library, which writes the hash |
| Scripts | `attachScript` for the witness set's native and Plutus scripts |
| Collateral | the UTxO set aside, as the builder's only collateral candidate, with its return at the change address; the builder reserves it against its own coverage target |
| Execution units | `setPlutusContext` with no execution-units estimate, so balancing prices the builder's hard-coded per-transaction maximum and lowers the fee after evaluation. The evaluator returns the intent's observed units for each redeemer. The cost models are empty lists, which change the script data hash's value but not its size |

Written on the transaction after the build, unpriced and unbalanced by the library, and named in a failure's detail: every certificate when one has no operation, a mint under a native script, votes, proposals, the treasury value, a donation, auxiliary data that is not metadata alone, witness-set datums that no spent script input takes, bootstrap witnesses, and observed vkey witnesses beyond the keys the library counted. A mint the library is not given fails its build, short of the token. An intent is not replayable for `lace-rrri` when it carries body field 6 or a redeemer no operation can attach: a vote or proposal redeemer, a certificate redeemer on a kind other than 2 and 7 or on certificates written after the build, or a mint redeemer on a mint written after the build. The builder's seed for execution units is a fixed 14,000,000 memory and 10,000,000,000 steps, so a script spend whose observed units exceed it can fail its build under both policies with class `fee-minimum` (`EvaluatedFeeShortfallError`), as one spend of the preprod probe histories does.

`adalite-lp` runs AdaLite's planner on each spend's whole request. The wallet's send screen pays one output holding ADA alone or one token, at the wallet's own minimum ADA, through `Account.getTxPlan`. The study drives the planner behind it with the request as it is: several outputs, several tokens and the requested coin. The adapter takes the wallet's `arrangeUtxos` from the `Account` and writes `selectMinimalTxPlan`'s loop out line for line over the bundle's `computeTxPlan` and `validateTxPlan`, with the requested outputs where the send screen's draft has its one output. That includes its test of the fee against the base fee, which compares two BigNumber objects by identity (`===`); the adapter keeps that comparison. On a one-output request the plan is `getTxPlan`'s. `validateTxPlan` holds a requested output to the wallet's own minimum, which prices the coin at 9 bytes, so an output at the ledger's minimum fails with the wallet's `OutputTooSmall` (class `other`) under both policies. A requested output with a datum or a reference script is not replayable, since the wallet's outputs cannot carry one. A redeemer or collateral (which comes only with redeemers) also makes the spend not replayable, since the wallet writes no script part and a part written after the build cannot be given a redeemer. The wallet writes the spend's TTL and validity start itself. It cannot write the other fixed parts, so the adapter writes them on the wallet's transaction after the build, unpriced: fixed inputs, reference inputs, certificates, withdrawals, the mint field, required signers, votes, proposals, the treasury value, the donation, auxiliary data with its hash, and the witness set's scripts, datums and bootstrap witnesses. The planner's balance leaves out the value such a part moves, so a fixed input, a withdrawal, a mint or a deposit fails the kit's balance check under `L/own`. When a requested output needs that value (a token only a mint supplies), the planner's own plan fails with class `balance` under both policies. Either failure names the part. The fee, the minimum ADA, the key deposit and the 16,384-byte and 4,000-byte limits are the wallet's constants, not the run's parameters. No package publishes the wallet, so `node scripts/build-adalite.mjs --clone <a clone of vacuumlabs/adalite>` (or `--fetch <new directory>`) compiles it. It checks the git object hashes of the pinned paths, of both manifests and of `yarn.lock` against `src/methods/adalite-source.mjs`. It bundles the modules the planner loads into `build/wallets/adalite/` (gitignored) with the pinned esbuild, and records the commit, the hashes and the bundle's SHA-256 beside them. The method refuses to load without that build, naming the script. The build makes two departures from compiling the files as they are, both recorded: a called namespace import of lodash or assert becomes a default import, which is what the wallet's webpack build gives; and the bundle declares a module-local `document` with no `data-config` attribute, so the configuration the page would supply is empty, which the planner never reads. The repository has no license file; its manifests declare ISC, and the build writes a NOTICE saying so beside the bundle.

`yoroi-lf` runs the wallet's own send flow, which takes outputs, a TTL and metadata and nothing else. A requested output goes in as the wallet's entry: its address, its coin and tokens, and a datum hash. The wallet writes every output in CSL's array form. The TTL comes from the wallet's clock, which the method sets to the intent's TTL less the 7,200 slots the wallet adds, so that the wallet writes the observed TTL. Metadata goes in as each label's JSON under CSL's BasicConversions schema, which the wallet encodes back. The method checks that the TTL and each label's metadatum come back byte for byte; the container form of the auxiliary data is the wallet's. The intent's other vkey witnesses are written after the build, unpriced. Every other part is not replayable for `yoroi-lf`: fixed and reference inputs, collateral, body fields other than the TTL (and so every implicit value), witness-set entries other than vkey witnesses, and a requested output with an inline datum or a reference script. Also not replayable: a TTL under 7,200 slots, auxiliary data holding a script, and metadata whose JSON form the wallet encodes to other bytes, such as an integer beyond 2^53. When the wallet's first build fails on the change output, the wallet rebuilds with the first output's ADA lowered, which pays less than the intent asks. `L/own` then records the spend as failed, with the class of that first failure, read from the wallet's log, whether or not a rebuild succeeded. A requested output that the wallet writes otherwise fails with class `other`: the wallet raises a token output's coin to at least 1 ADA, and it leaves out of every value it writes a token whose asset name is empty. An input holding such a token gives a transaction whose assets are not conserved, which the kit fails with class `balance`.

`apollo-macs` passes each part through an operation of Apollo's builder in its Go helper: fixed inputs by `AddInput`, a script input by `CollectFrom` with its redeemer, reference inputs, native and Plutus scripts by `AttachScript`, datums by `AddDatum`, the mint by `Mint` (with the policy's redeemer for a Plutus policy), certificates, withdrawals by `AddWithdrawal` (with the account's redeemer for a script), votes, proposals, required signers, validity, the treasury fields, and the metadata. The collateral is the UTxO set aside, given by `AddCollateral`; the builder then chooses none and sizes the total collateral and the return from its fee. The execution units come from the chain context's evaluator, which returns the intent's observed units; Apollo raises each by its 20 percent buffer and prices the raised units, as it does with any evaluator. A script spend that also lists required signers cannot be evaluated in the replay, because Apollo signs the evaluation draft for each signer and checks the signatures, so the adapter gives the builder the observed units raised by the same buffer with its estimate off, which writes the same redeemers. Not replayable for `apollo-macs`: body field 6, a body field no operation writes, a bootstrap witness, auxiliary data holding scripts, and a certificate's, a vote's or a proposal's redeemer, since the builder attaches redeemers to spent inputs, minting policies and withdrawals only.

### Builder survey

`src/survey/` holds the library part of the builder survey. Its fixture (`fixture.mjs`) is a wallet of k UTxOs, k from 1 to 5, each with 141 one-unit tokens of its own test policy under 32-byte names (a 4,974-byte Value) and 100 ADA. The wallet comes with and without two pure-ADA UTxOs of 2k × 100 ADA each, which alone cover the payment: 75% of the wallet's ADA to an external key address. Both variants, for k from 1 to 5, together hold 9,000 ADA, within one 10,000 tADA preprod faucet request. Names, policies and transaction ids are BLAKE2b hashes of fixed texts. These values are the survey's own settings, `SURVEY_SETTINGS` in `src/survey/fixture.mjs`, kept apart from the tables under Settings; `pureEach` and `names` refuse any value but their one implemented.

The subjects are the baselines, CSL with `prefer_pure_change` set (`csl-lf-pure` and `csl-ri-pure`, `cslMethod` with `preferPureChange`), Mesh (`@meshsdk/transaction` 1.9.1) at its default selector and with its `LargestFirstInputSelector`, driven through `MeshTxBuilder` offline with Mesh's own constraint callbacks (`src/methods/mesh.mjs`), and the Evolution SDK with its `unfrack` option at the option's defaults. A random subject runs 30 times (seeds 1 to 30 where it takes one). Every transaction a subject builds goes through the kit's checks; one the kit rejects is recorded as built but invalid, with the reason. `mesh-compare.mjs` compares Mesh's default with `cjs-rrri` on payments over the shapes, both given the same seeded draws.

## Settings

Where a rule admits more than one reading, the reading is a named setting whose default is the reading this code uses; `--set` changes it, and the value is recorded in every history file's header. A value that is not implemented is refused.

| Setting | Default | Meaning |
|---|---|---|
| `requested` | `a` | Requested outputs as observed, plus the inflow of native assets as requested wallet outputs. `c`: outputs to other stake credentials only. |
| `heldConsumed` | `a` | A held UTxO leaves the state when any transaction consumes it; consumed by the wallet's own spend, it is a fixed input. `b`: held UTxOs never leave. |
| `mainnetBytes` | `immutable-db` | Mainnet transaction bytes come from the node's ImmutableDB. |
| `scriptFee` | `snapshot` | Both script-fee terms under the snapshot's parameters, once per intent. |
| `fixedBytes` | `per-intent` | The bytes of the fixed parts, once per intent. |
| `phase2Invalid` | `forfeit` | A phase-2-invalid spend forfeits its collateral. `skip`: not written. The replay engine replays every phase-2-invalid intent a history holds as a forfeit, so this setting alone decides whether they are written. |
| `assetClass` | `profile` | Units for an asset's class: the largest of the holdings at the window's start and end and the units moved. `at-spend`: the holding just before the spend. |
| `valueBytes` | `ledger` | Value bytes by the ledger's serialization. |
| `inflowIncludesAda` | `false` | ADA inflow reaches the change through the implicit input and is not a requested output. |
| `typeAssets` | `outflow` | Spend types read the requested outputs other than inflow outputs, or the inflow outputs when there is no other. |
| `t5ScriptOrders` | `contents` | A requested output at a script address makes a spend T5 only when it carries a fungible token. `any-script-output`: whatever it carries. |
| `burstMinSpends` | `2` | A lone spend carries no burst. |
| `burstGapSeconds` | `60` | The burst gap. |
| `markSeconds`, `markBeforeTies` | 30 days, `true` | The mark interval, and whether a mark at an event's exact time comes first. |
| `outputForm` | `auto` | A UTxO re-encoded from db-sync's columns takes the map form when an inline datum or a reference script needs it, the array form otherwise. |
| `chunkSlots` | `21600` | ImmutableDB chunk size in slots. |

After the final freeze, `history` refuses a wallet outside `study.sample`, given by id or by stake address, before any of its rows is read, and reads a wallet of the sample; a confirmation-split wallet still needs `--analysis-freeze-tx`; `--from-study all` reads the sample; and a role that cannot read `study.sample` reads nothing. `census` and `near-cap` refuse `--all-wallets` and a wallet outside the sample, near-cap's `--from-study` reads the random samples and the census's reads the recent frame. In a live-fire run, `history` reads the pick's wallets and no study table, refuses any other wallet, `--from-study` and `--all-wallets`, and a pick for another network is refused. On a test network outside a live-fire run nothing is restricted.

`test/unit/queue/run-queue.test.mjs` runs the job queue over small Node scripts, without the treatment or a database. It checks job order, resuming past done jobs, stopping at a failure and `--continue-on-failure`, a timeout that ends the job and a grandchild it started (and SIGKILL for a group that ignores SIGTERM, only after the grace period from the SIGTERM the job saw, an attempt whose job was not yet ready run again with a longer limit), `before` and `after`, `pauseAfter`, the lock held and stale, refusal of invalid queues before anything runs, env files and their precedence, an interrupted job and `--rerun-interrupted`, SIGTERM to the runner, a state file that is never half-written, `status`, `idle` and `--detach`.

`test/unit/study/live-fire.test.mjs` runs the `live-fire` command over stand-in commands and a stand-in gate, without a database, with the extraction run's entries and pick written to a temporary `RESEARCH_CORPUS_HOME`. It checks the refusals before anything is logged or queried: no pick, a pick on another network, no live-fire start entry, an end entry that kept no pick, a pick a cleanup deleted, no `sim/wallets.json`, one for another network, and one with no snapshot. A refused database gate leaves a failed query and no `sim-live-fire-start` entry, and the options are refused before the pick is read. A clean run runs its stages in order with the pick's wallets and block, one repetition, the study's watchdog and validity checks. Its start and end entries carry their fields in order, its chain holds, its directory is deleted, and no stake address or count reaches the log or the print. The three checks follow a validity failure, work a watchdog set aside, a history check failing and a database error. Error text carrying an address, a hash, a wallet id and counts reaches the log redacted, and the redaction keeps no name of this code whole: the code has no name with a part that begins with a digit, and `CODE_NAMES` is empty. The output is deleted on success and on failure. `--keep-for-debug` keeps a failed run until `--cleanup`, which is refused for an unknown run and for one with nothing to settle; a failed deletion is logged. A run killed in a stage, in a process of its own, leaves its start unclosed until `--cleanup` closes it.

`test/unit/study/live-fire-corpus.test.mjs` runs the extraction tool's own code over logs the `live-fire` command wrote, with the extraction's entries written by that tool's own `appendEntry`. Its `verifyLog` reports no error, unclosed start or failed deletion after a clean run and a refused gate, and lists as kept only the extraction run that kept the pick. It lists a kept simulator run until its cleanup, a killed run's start until its cleanup, and a failed deletion until its cleanup. The two tools' redactions agree on sample error texts. The final-freeze check, on a chain of signed records in PGlite, fails `live_fire_after_hypotheses` when the simulator's start, as the first live-fire run of the log, is dated before the hypotheses block, and passes when it is dated after; over the whole log, the extraction's start comes first. These tests need the extraction tool's directory, with its dependencies installed, beside this one or named by `RESEARCH_SIM_CORPUS_TOOL`, and are skipped without it.

`test/unit/core/controls.test.mjs` checks the four controls on a constructed transaction, each caught by its own check, also when a required signer is not the input's key, and that a transaction with no outputs has no fee or value control. `test/unit/history/draw.test.mjs` checks, on hand-built extraction rows, the draw fields of each size group, a wallet whose window holds exactly 1,000 transactions (not capped) and one that holds 1,001 (capped, its history ending at its 1,000th), an uncapped wallet's history ending at the window's last transaction, the run-level counts of two frames, a transaction count that differs from the extraction's, and the refusal of an extraction run without the draw's columns. `test/unit/history/sample-header.test.mjs` checks that the `study_samples` rows reach the header's `sample` field per frame. `test/unit/history/refusals.test.mjs` checks the history command's refusals before any wallet is read (`refuseWallets`): an excluded wallet is refused, a confirmation-split wallet is refused without `--analysis-freeze-tx` and accepted with it, and a wallet outside the study samples is accepted.

`npm run test:treatment` runs every file in `test/treatment/`, one at a time. Each needs the treatment (`RESEARCH_SIM_TREATMENT_DIR`, and `RESEARCH_SIM_TREATMENT_PINS` when the digest list is not `data/treatment-pins.txt`) and is skipped without it. The bridge, shapes, replay, repeat, limits and timing files test:

- the bridge against a fresh run of the treatment harness's own runners, plan for plan and result for result, on a digest-checked copy;
- every transaction built on the 21 shapes (plans, and payments by the H-12 rule and by the test method under the layout change) meeting the kit's checks, read back by CSL to the same bytes, at exactly the ledger's minimum fee when the treatment built it, with the four negative controls caught on each;
- the replay engine on every shape's synthetic stream under every entry of the study's plan, each replayed transaction checked, read by CSL and its negative controls caught, and its events in place;
- the conforming share (`conform-share.test.mjs`): the state-derived Value bytes and minimum coin equal CSL's on every UTxO of the 21 shapes at the start and after the planner's plan, the counts equal the treatment's `walletLayoutReport`, the class map equals the plan's, M7's partial-split remainder is the one UTxO of those states that does not conform, and a hand-built UTxO breaking one rule at a time fails for that rule alone, the coin-free count differing only for the coin rule;
- a replay run repeated through the worker pool with the same seeds writing byte-identical records, and `cjs-rrri`'s replay jobs writing byte-identical records for the same seeds whether two workers run every job or a fresh worker runs each, with the records for seeds 1 and 2 differing;
- the validity mode on S1 and CL1: every transaction counted, read by CSL and caught by each control, a replay equal with and without it once the `validity` field is removed, and a transaction checked against a state it does not spend from failing with its position (`validity.test.mjs`);
- the watchdog, forced (`limits.test.mjs`): `test-stall` blocking for 3 seconds on S1's first intent, under a 2-second watchdog. It is stopped once and runs again to completion in a fresh worker, and the records are byte for byte those of the same run under the default watchdog, with no time-out and no time-limit failure;
- the records independent of how the jobs run (`machine-independence.test.mjs`): the replays of the study's recent plan, over S1, S8 and M1. Each runs three ways: one worker running every job, three workers each replaced after one job, and the same with a 1-second watchdog that stops each stalling `test-stall` job and any other job past it. The three write the same records, byte for byte once `csl-ri` is set aside, and its records agree in keys and counts;
- timing and memory of a plan, a set of payments and a replay on M2, M3 and E1.

The same script's baseline and survey files: `baselines-behavior.test.mjs` checks the library behaviors the adapters rely on, each on a constructed case, and one failure of each class per adapter. `baselines-payments.test.mjs` runs every baseline, at its default change and under the layout policy, on a set of payments (`test/lib/payments.mjs`: ADA payments, one NFT and shares of the ADA balance) on the observed and the tidied layout of the 21 synthetic shapes (the 17 seeded shapes plus CL1, CL3, E1 and E2): each transaction meets the kit's checks or fails one with its class, and the kit's negative controls are caught on each in its library's encoding. The same test measures cardano-js-sdk's callbacks against the assembled transactions, the build times on the largest shapes, M2 and M3 (3,005 UTxOs each) and E1 (405 UTxOs), and determinism by seed and by run. `survey.test.mjs` runs the builder survey and the Mesh comparison, the latter on the same set of payments. With `RESEARCH_SIM_OUT` naming a directory, these write their records there as JSON.

`npm run test:preprod` runs the integration tests against a preprod database, as of one snapshot block (`RESEARCH_SIM_SNAPSHOT`), since db-sync keeps following the chain while they run; their environment is described in `test/integration/history/env.mjs`. They cover:

- the reconstruction against the reference query, for the seeded wallets and 1,000 random wallets at 20 blocks;
- outputs re-encoded from db-sync's columns against their original bytes, by output form;
- the 17 seeded shapes against the preprod seeder's specification (`tools/preprod-seeder`, used through its `address` command and its deterministic generator only), and the shapes' own spends as intents; a UTxO whose creating transaction spends no input of the funder or of a shape, sent by someone else, is left out of the comparison and reported;
- every spend of the seeder's funder and of 200 further wallets over the last 60 days, with the burst cases they contain, each file read back by the simulator's reader with every record's creating transaction id checked against db-sync's;
- phase-2-invalid transactions;
- the ImmutableDB against `tx_cbor`, byte for byte, across every Shelley-based era;
- the census, near-cap and collateral commands, with their plans and run times.

Results go to `preprod/<RESEARCH_SIM_TEST_TAG>/tests/` under the output root.
